# Agent-generated script workloads: ranked taxonomy, code-mode scenario matrix, and benchmark tasks (as of 2026-11-13)

Labels used throughout: **Measured** = I measured it from the research host on 2026-11-13 (single samples, indicative only). **Computed** = I computed it from a public dataset. **Vendor claim**, **Anecdote**, and **Inference** are marked where they apply. Task IDs (T1 to T38) are specified in section 3. Matrix cells (M1 to M14) are specified in section 2.

## 1. Ranked taxonomy: which workloads do agent-generated scripts run, how common is each, and which cost dominates?

### Takeaway
The best-documented workload is code-mode host-tool orchestration (serial chains, parallel fan-out, pagination, retries) combined with in-sandbox filtering of large tool results. Tabular data analysis, grep-style text search, web fetch with extraction, and chart and document generation follow. Beyond the five starting categories, the evidence supports adding: large-payload marshaling, tool-catalog (binding) scaling, OpenAPI spec search, persistent sessions with idle waiting and snapshot/resume, date/time and encoding/HMAC/compression utilities, embedded SQL, sub-LLM calls from code, document and image parsing, PII redaction, and cancellation and output-cap behavior.

**Ranked taxonomy table.** Rank reflects the strength and breadth of frequency evidence across code mode, code interpreters, and bash agents, weighted toward code mode. "Dominant cost" is an inference argued in section 10. Tiers: A = portable (host tools plus stdlib only), B = needs ecosystem libraries, C = shell.

### Inferences
- **Ranking method (Inference).** Rows 1–3 are what code mode exists to do and are the user's main use, so they rank first even where frequency is shown by design documents rather than telemetry. Rows 4–7 have quantitative benchmark or trace evidence. Rows 8–18 have product or benchmark evidence but small or unknown shares.
- **New categories beyond the five starting ones (Inference):** (a) large-result marshaling (T6, T11) deserves its own axis because the dominant cost is boundary conversion, not analysis; (b) tool-catalog scaling (T10) because binding setup scales with catalog size; (c) sessions, idle waiting, and snapshot/resume (T25, T26) because platforms bill and cap by container time and idle state; (d) utility compute (dates, hashing/HMAC, compression, regex redaction) that appears in a few percent of tasks but stresses interpreter speed when no native library exists; (e) sub-LLM calls (T27); (f) limits and output behavior (T28, T29).
- **Tiering (Inference).** Monty has no third-party packages and a partial stdlib ([Monty limitations](https://pydantic.dev/docs/monty/limitations/)), and Dynamic Workers favor JavaScript for small snippets ([Cloudflare](https://blog.cloudflare.com/dynamic-workers)). Library-heavy workloads (pandas, matplotlib, office formats) therefore cannot run identically everywhere. Each Tier B task should have a Tier A twin with the same expected output (T15 and T32, T30 and T33), so every runtime gets a score and library-equipped runtimes also get a library score.
- **Priority (Inference):** P1 = T1–T6, T10, T12, T15, T17, T25, T26, T28, T30; P2 = T7–T9, T11, T14, T16, T18–T23, T27, T29, T31–T35, T38; P3 = T13, T24, T36, T37.

### Gaps
- No public telemetry gives the workload mix inside code-mode or code-interpreter traffic (share of scripts that fetch, analyze, generate files, and so on). The ranking relies on benchmarks, design documents, and agent traces.
- The ChatGPT data-analysis share could not be verified from the primary paper (OpenAI's page returned 403).
- BigCodeBench is a curated benchmark, not production usage. Its library mix is a proxy for what LLM-written utility code imports.

## 2. Code-mode scaling scenario matrix: how should the suite vary tool calls, call shapes, latency, payload, and tool-catalog size?

### Takeaway
Cover N = 1, 10, 100, 1000 calls in eight shapes (serial chain, unbounded and bounded fan-out, fan-out then aggregate, pagination, retry, nested, polling) at four latencies and three payload sizes, plus tool catalogs of 10, 100, 1,000, and 3,778 bindings in three binding modes. Every cell makes real HTTP(S) requests to a deterministic fixture server through one of three HTTP paths, and runs at 1 to 1,000 concurrent sessions to measure marginal RSS and CPU.

### Cited Findings
- **Calls per task in agent benchmarks:** MCPMark averages 16.2 execution turns and 17.4 tool calls per task over 127 tasks ([MCPMark, ICLR 2026](https://huggingface.co/papers/2509.24002); the ICLR abstract gives 16.18 and 17.38). Toolathlon: 108 tasks over 32 apps and 604 tools, about 20 turns on average; the best model averaged 20.2 tool-calling turns and succeeded on 38.6% ([Toolathlon, v1 2025-10-29](https://arxiv.org/abs/2510.25726)). AppWorld: 9 apps, 457 APIs, 750 tasks; 9.5 unique APIs per task on average (max 26); 42.5 API calls (max 244) and 41.3 solution lines (max 134) on Test-N*, 46.8 calls (max 649) and 56.9 lines on Test-C ([AppWorld, ACL 2024](https://arxiv.org/html/2407.18901)). Manus: ~50 tool calls per typical task and a ~100:1 input-to-output token ratio ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)).
- **Code execution collapses turns:** in a study on 10 MCP-Bench servers (94 tools), traditional MCP "often requires dozens of turns," while the code-execution variant "aggregates most tasks into a single execution turn," with lower average latency but more latency outliers during dynamic tool discovery ([arXiv 2602.15945, 2026-02-17](https://arxiv.org/html/2602.15945)).
- **When code mode pays off (Anthropic):** strong fit for fan-out across many items, large filterable results, and agentic search; weak fit for strictly sequential workflows and for a few small calls, where "container and script overhead can exceed the savings." On τ²-bench, with 1–2 sequential calls per turn, PTC left scores unchanged and cost about 8% more. On a 75-tool project-management benchmark it cut billed input tokens by about 38% ([PTC docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)).
- **PTC's worked example:** 20 team members, 50–100 expense line items each, 2,000+ items (50 KB+), about 200 KB raw reduced to about 1 KB of output; `asyncio.gather` for parallel fetches; 20+ calls in one code block remove 19+ inference passes ([Anthropic, 2025-11-24](https://www.anthropic.com/engineering/advanced-tool-use)).
- **Tool catalogs:** example five-server setup GitHub 35 tools (~26K tokens), Slack 11 (~21K), Sentry 5 (~3K), Grafana 5 (~3K), Splunk 2 (~2K), totaling 58 tools ≈ 55K tokens; Jira alone ~17K; 134K tokens of definitions seen before optimization ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)). Tool selection accuracy degrades past 30–50 tools; tool search loads 3–5 ([tool search docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)). Remote MCP servers: 1,412 servers, 4,126 tools, mean 13.4, median 5, nearly half expose 4 or fewer, 93% use Streamable HTTP ([Bloomberry](https://bloomberry.com/blog/we-analyzed-1400-mcp-servers-heres-what-we-learned/)). MCPZoo: 37,288 servers accepted protocol interaction; 85.53% expose fewer than 10 tools; the largest aggregator exposes 8,816 ([MCPZoo](https://huggingface.co/papers/2607.11086)). Benchmarks: MCP-Bench 28 servers / 250 tools ([MCP-Bench](https://huggingface.co/papers/2508.20453)); MCP-Atlas 36 servers / 220 tools / 1,000 tasks ([MCP-Atlas](https://arxiv.org/abs/2602.00933)).
- **Large catalogs as specs (Measured, 2026-11-13):** Cloudflare's `openapi.json` is 28.0 MB with 2,356 paths, 3,778 operations, and 7,145 component schemas ([cloudflare/api-schemas](https://raw.githubusercontent.com/cloudflare/api-schemas/main/openapi.json)); Cloudflare's blog describes "over 2,500 endpoints" and 1.17 million tokens without Code Mode versus ~1,000 tokens with it, while the page description says over 2 million ([Cloudflare](https://blog.cloudflare.com/code-mode-mcp/)). GitHub's REST description is 14.3 MB with 841 paths, 1,280 operations, 1,014 schemas ([github/rest-api-description](https://raw.githubusercontent.com/github/rest-api-description/main/descriptions/api.github.com/api.github.com.json)).
- **Platform limits that shape fan-out:** Workers: 128 MB memory per isolate; CPU per HTTP request 30 s by default, up to 5 min; subrequests 50 (Free) and 10,000 (Paid default); 6 simultaneous open connections, with a seventh queued until one receives headers ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)). Claude: each REPL cell has a 90-second wall-clock limit with PTC; a pending tool call raises `TimeoutError` after about 4 minutes (270 s in the doc's example); each programmatic call counts toward rate limits individually ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool); [PTC docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)). Monty's asyncio surface is `run`, `gather`, and `sleep`, with no event loop inside the sandbox ([Monty limitations](https://pydantic.dev/docs/monty/limitations/)).
- **Startup reference points:** Monty 0.80 ms for a new sandbox from a pool and 0.40 ms for 10 REPL commands; WASI/wasmtime 16 ms and 180 ms; local Docker 195 ms and 700 ms; a sandboxing service 1,500 ms and 400 ms; Pyodide in Deno 2,700 ms and 35 ms (vendor table, [Monty docs](https://pydantic.dev/docs/monty/)). Isolates start in "a few milliseconds" with "a few megabytes" vs containers' hundreds of ms and hundreds of MB (vendor claim, [Cloudflare](https://blog.cloudflare.com/dynamic-workers)).

### Inferences
- **Mapping grid values to evidence (Inference).** N = 1 to 10 covers typical code-mode and τ²-like scripts; N = 100 covers AppWorld-scale and PTC fan-out examples; N = 1000 stresses the upper tail (AppWorld challenge max 649). C = 10 is one or two typical MCP servers; C = 100 is a multi-server agent (benchmarks use 94–604 tools); C = 1000 to 3,778 is a whole large API (GitHub, Cloudflare).
- **Catalog sizes in bytes (Inference).** 55K tokens for 58 tools is about 950 tokens per JSON-schema tool definition; at ~4 characters per token, 1,000 tools is roughly 3.8 MB of definitions. The GitHub spec averages ~11 KB per operation and Cloudflare's ~7.4 KB, including shared schemas. If a runtime type-checks scripts against declarations, startup scales with C; Monty's limitations page says absent names "fail type checking," so it type-checks ([Monty limitations](https://pydantic.dev/docs/monty/limitations/)).
- **The 6-connection cap matters (Inference).** A 1,000-way `Promise.all` of `fetch` inside a Worker would queue behind 6 open connections, so PARb c = 6 reproduces a real platform constraint, and runtimes that implement fan-out through host tools may avoid it.
- **Real HTTP but deterministic (Inference).** Public endpoints vary in latency and impose rate limits, so the default target is a self-hosted fixture server over real TCP/TLS with injected latency, plus an optional internet profile using the pinned public endpoints in section 5 for realism checks (not for scoring).
- **Measurement protocol (Inference).** Baseline RSS = runtime host process with 0 sessions. Marginal RSS per session = (RSS at K sessions − baseline) / K, sampled during the waiting phase (M3, M4, M11, T26) and after completion for retained sessions. Per-call overhead = slope of wall time and CPU vs N at L0 (M2). Memory per pending call = slope of RSS vs N in M4. Report CPU-seconds per script, p50/p99 wall time, bytes crossing the boundary, and bytes returned to the caller (reduction ratio, as in Anthropic's 200 KB to 1 KB example).

### Gaps
- No public production distribution of tool calls per script, script length, script run time, or per-call payload size exists for Code Mode, PTC, or Monty. N values are anchored on benchmarks and vendor examples.
- Cloudflare does not document how much of its 28 MB spec its `search()` sandbox holds in memory against the 128 MB isolate limit, or the `DynamicWorkerExecutor` timeout defaults.
- I found no data on how often models write sequential loops versus parallel fan-out when calls are independent. Vendor examples show both.

### Inferences
All task definitions below are design proposals (Inference). Sizes cite the measurements above where real.

**Conventions for every task**
- Seed `20261113`; fixed clock `now = 2026-10-31T00:00:00Z`; UTF-8 everywhere.
- Output: canonical JSON (sorted keys, no whitespace, floats rounded to 6 decimals, money to 2); ties broken by ascending `id`. Expected outputs come from a reference implementation over the seeded fixtures; implementations must match byte-for-byte.
- Regexes use the RE2-compatible subset (no backreferences or lookaround) so Python `re`, JavaScript `RegExp`, Rust `regex`, and Monty's `fancy-regex` agree.
- Host tools are async functions taking one object/dict argument. Each task runs in two marshaling modes: string (tool returns raw response text) and structured (host returns a parsed value).
- Each run records: wall time, CPU-seconds, peak and steady RSS, bytes across the boundary, bytes returned, number of HTTP requests (verified by the fixture server's per-session counters).

**Fixture server ("agent-fixture")**
- HTTPS (benchmark CA installed in sandboxes) and HTTP; HTTP/1.1 keep-alive; optional gzip (`?gzip=1`).
- Latency injection before headers via `?lat_ms=` (L0, L50, L300, L2000), deterministic per request.
- Datasets: **D1** records: 500k seeded records `{id, region (8 values), category (25 values), amount (lognormal μ=3 σ=1, 2 dp, 3% negative), ts (ISO-8601 UTC in 2026-01-01..2026-10-31), status (open 50%/closed 40%/pending 10%), next_id (a permutation), pad}`, ≈100 B minified per record without `pad`, so 50k records ≈ 5 MB. **D2** issues: 5,000 GitHub-shaped issues in two profiles, compact (≈1.3 KB, HN-like) and github (≈4.3 KB, GitHub-like). **D3** HTML: 20 byte-pinned pages (10 near 35 KB, 8 near 155 KB, 2 near 1 MB). **D4** the pinned COVID CSV (or a synthetic CSV with the same shape if licensing requires). **D5** the pinned Gutenberg text. **D6** a pinned ~4 MB CC-BY PDF. **D7** pinned GitHub and Cloudflare OpenAPI specs. **D8** CPython v3.14.0 `Lib/`. **D9** 68,000 synthetic issue/PR JSON files (~1.5 KB each, ≈100 MB). **D10** 10,000 × 384 float32 unit vectors plus 20 queries. **D11** a dirty CSV: 100k rows × 12 columns with 2% missing numerics, 1% duplicate rows, three date formats, 0.5% injected outliers.
- Endpoints: `GET /items/{id}` (D1 padded to 1 KB); `GET /export?records=5000|50000|500000`; `GET /issues?cursor=&limit=100&profile=` (with `next_cursor` and a `Link` header); `GET /teams/{t}/members`, `GET /users/{id}/expenses?quarter=`, `GET /budgets/{level}`; `GET /flaky/{id}`; `GET /orgs/{o}/repos`, `GET /repos/{r}/pulls`, `GET /repos/{r}/pulls/{n}/reviews`; `POST /jobs`, `GET /jobs/{id}`, `GET /jobs/{id}/result`; `GET /pages/{name}.html`; `POST /graphql`; `GET /files/{name}`; `POST /llm`; `GET /slow?ms=`.

## 4. What do code-mode scripts look like in practice?

### Takeaway
Published examples are short (roughly 5–60 lines) async scripts that call 1 to ~25 host tools, often in a plain `for` loop with sequential `await`, sometimes with `gather`/`Promise.all`. They parse JSON, filter or aggregate, and print or return a result that published examples show as 75–2,000× smaller than the raw tool output. No vendor publishes production distributions of calls per script, run time, or payload size.

### Cited Findings
- **Cloudflare Code Mode (2025-09-26):** the agent gets "just one tool, which simply executes some TypeScript code"; MCP schemas become a TypeScript API with doc comments; bindings are RPC calls back to the agent loop; output is returned via `console.log()`; a new isolate is created per snippet and discarded, with no pooling or prewarming; `fetch()` and `connect()` throw inside the sandbox ([Cloudflare](https://blog.cloudflare.com/code-mode/)).
- **Cloudflare Code Mode MCP server (2026-02-20):** two tools, `search()` and `execute()`, cover the whole API in about 1,000 tokens. `search()` loops over `Object.entries(spec.paths)` filtering, for example, paths containing `/zones/`. `execute()` examples make one or two sequential `await cloudflare.request(...)` calls, with no `Promise.all`; the WAF/DDoS walkthrough took four tool calls in total ([Cloudflare](https://blog.cloudflare.com/code-mode-mcp/)).
- **Cloudflare codemode docs:** the `code` tool's description holds generated TypeScript declarations for every upstream tool; the example loops over projects with sequential `await` and filters blocked tasks; upstream errors become catchable exceptions; final responses are capped near 6,000 estimated tokens and marked truncated, so code "should filter and paginate before returning" ([Cloudflare docs](https://developers.cloudflare.com/agents/model-context-protocol/codemode/)).
- **Dynamic Workers (2026-03-24):** the example agent calls `env.CHAT_ROOM.getHistory(1000)` and returns only one author's messages; another example searches files, plans several edits, and applies them atomically; APIs are TypeScript interfaces bridged by Cap'n Web RPC; Zite's LLM writes TypeScript CRUD apps and integrations (Stripe, Airtable, Google Calendar) and serves "millions of execution requests daily" ([Cloudflare](https://blog.cloudflare.com/dynamic-workers)).
- **Anthropic code execution with MCP (2025-11-04):** tools appear as a file tree (`./servers/google-drive/getDocument.ts`); a meeting transcript moves from Drive to Salesforce without entering the model (150,000 to 2,000 tokens, 98.7%); a 10,000-row spreadsheet is filtered to 5 rows; a loop polls Slack until a deployment message appears; intermediate results go to files such as a CSV; reusable code is saved under `./skills/` ([Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)).
- **Anthropic PTC docs:** tools become async Python functions that take one dict and return a string (`rows = json.loads(await query_database({"sql": ...}))`); documented patterns: a loop over 5 regions summing revenue, early termination over health checks, conditional tool choice on file size (<10,000 bytes), and filtering logs to `ERROR` lines and returning the last 10. Calling 10 tools directly uses roughly 10 times the tokens of calling them programmatically and returning a summary. Programmatic tool results do not count toward token usage ([PTC docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)).
- **Anthropic advanced tool use (2025-11-24):** the budget example uses `asyncio.gather`; average tokens fell from 43,588 to 27,297 (37%) on complex research tasks; knowledge retrieval rose from 25.6% to 28.5% and GIA from 46.5% to 51.2%; Claude for Excel uses PTC for spreadsheets with thousands of rows ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)).
- **Dynamic filtering (2026-02-17):** Claude writes code to filter web search and fetch results; BrowseComp rose from 33.3% to 46.6% (Sonnet 4.6) and 45.3% to 61.6% (Opus 4.6); DeepSearchQA F1 from 52.6% to 59.4% and 69.8% to 77.3%; a customer describes the model "writing Python to parse, filter, and cross-reference results" ([Claude blog](https://claude.com/blog/improved-web-search-with-dynamic-filtering)).
- **Monty:** the README example calls a host `nutrition` function and does arithmetic on the result; host callables are passed as `external_lookup`; the sandbox has no filesystem, environment, or network ([Monty README](https://github.com/pydantic/monty)).
- **smolagents CodeAgent:** the local executor walks the AST, disallows imports outside an allowlist (base list: statistics, itertools, time, queue, collections, math, random, re, datetime, stat, unicodedata), and stops `while` loops after 1,000,000 iterations ([smolagents](https://huggingface.co/docs/smolagents/tutorials/secure_code_execution)).
- **Turn collapse:** code execution "aggregates most tasks into a single execution turn," but failed programs are regenerated and rerun, and global errors need full regeneration ([arXiv 2602.15945](https://arxiv.org/html/2602.15945)).
- **Proxies for script size:** BigCodeBench solutions average 10.0 lines ([paper](https://arxiv.org/html/2406.15877v4)); AppWorld solutions average 41.3 lines (max 134) ([AppWorld](https://arxiv.org/html/2407.18901)).

### Inferences
- **Archetype (Inference):** 10–60 lines; 1 discovery or list call, then a loop or fan-out of 5–100 calls; `JSON.parse`/`json.loads` per result; filter, group, or sort; return or print ≤6 KB. Both sequential loops and `gather` appear in vendor examples, so the benchmark must handle naive serial loops (memory held while waiting) and wide fan-out (memory per pending call).
- **Reduction ratios (Inference):** showcase examples reduce data 75–2,000× (150,000 to 2,000 tokens; 200 KB to 1 KB; 10,000 rows to 5), while aggregate token savings are 20–40% in production traffic, so most real scripts are smaller than the showcases.
- **Error paths matter (Inference):** regeneration loops mean the same script may run several times with exceptions thrown from host calls, which argues for T7 and T28.

### Gaps
- No distribution of tool calls per script, script length, run time, payload sizes, or serial vs parallel share from production Code Mode, PTC, or Monty traffic.
- No published code-mode script corpus suitable for replay.

A runtime-embedded client pays gzip decode and TLS inside the sandbox; the host-engine path pays them in the host and marshals decoded bytes. M13 should compare both.
- **Latency profiles (Inference):** L50 approximates CDN-backed and same-region APIs (27–112 ms measured), L300 approximates dynamic third-party APIs (226–574 ms measured), and L2000+ approximates slow tools and sub-LLM calls.

- No source measured the response sizes or latencies of tools agents actually call in production; the table is a sample of plausible public resources from one host.
- I found no evidence on how often agents use GraphQL versus REST.

## 6. What do code-interpreter and data-analysis agents do, and which libraries dominate?

### Takeaway
Pandas and NumPy dominate, followed by matplotlib/seaborn, scikit-learn, SciPy, and stdlib staples (os, re, collections, json, datetime, random, csv). The work is mostly summary statistics, correlation, distributions, cleaning, group-by, and charts on CSV/XLSX files of thousands of rows; enterprise SQL tasks (Spider 2.0) and spreadsheet modeling (DSBench) form a harder tail.

### Cited Findings
- DS-1000 counts by library and BigCodeBench library shares: see section 1 ([DS-1000](https://github.com/xlang-ai/DS-1000); [BigCodeBench dataset](https://huggingface.co/datasets/bigcode/bigcodebench), Computed).
- DABench concept counts and file shapes (9,639.7 rows × 10.6 columns average): see section 1 ([DABench](https://arxiv.org/html/2401.05507v3)). DABench names pandas (`pd.read_csv`), sklearn (linear regression, `train_test_split`), numpy histograms, and Python's `statistics` module (same source).
- DA-Code task split (EDA 60%, wrangling 20%, ML 20%): see section 1 ([DA-Code](https://arxiv.org/abs/2410.07331)).
- DSBench: 466 data analysis tasks and 74 data modeling tasks from ModelOff and Kaggle competitions; the best agent solved 34.12% of analysis tasks ([DSBench](https://arxiv.org/abs/2409.07703v2); via a search summary). ModelOff being a spreadsheet competition is my background knowledge, not from the source.
- Spider 2.0: 632 enterprise text-to-SQL workflow tasks on BigQuery, Snowflake, and local databases, often with over 1,000 columns and SQL over 100 lines; o1-preview solved 21.3% ([Spider 2.0](https://arxiv.org/abs/2411.07763)).
- Claude code execution environment: 5 GiB RAM, 5 GiB disk, 1 CPU; preinstalled pandas, numpy, scipy, scikit-learn, statsmodels, matplotlib, seaborn, pyarrow, openpyxl, xlsxwriter, xlrd, pillow, python-pptx, python-docx, pypdf, pdfplumber, pypdfium2, pdf2image, pdfkit, tabula-py, reportlab, img2pdf, sympy, mpmath; CLI tools unzip, unrar, 7zip, bc, rg, fd, sqlite; no internet; $0.05 per container-hour after 1,550 free hours, free when web search or fetch is in the request ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool)).
- OpenAI Code Interpreter: data analysis, coding, and math in a sandboxed container; memory tiers 1g (default), 4g, 16g, 64g; containers expire after 20 minutes without use, losing in-memory Python state; inputs include csv, json, xml, txt, pdf, doc/docx, pptx, xlsx, images, tar, zip, pkl, and code files; generated charts and CSVs come back as `container_file_citation` annotations; the model can crop, zoom, rotate, and read pixels of images; a 100 RPM per-organization rate limit is listed ([OpenAI docs](https://developers.openai.com/api/docs/guides/tools-code-interpreter)).
- AppWorld: 9 apps (457 APIs, 101 database tables); solutions use loops and other control flow and the engine returns paginated search results ([AppWorld](https://arxiv.org/html/2407.18901)).
- Consumer context: about 4.2% of ChatGPT messages involve programming ([UNU C3 summary of the NBER paper](https://c3.unu.edu/blog/what-over-2-5-billion-daily-messages-reveal-about-how-people-use-chatgpt)).

### Inferences
- **Dataset sizes (Inference):** benchmark files are small (thousands to tens of thousands of rows), so the 161,568-row CSV in T15 and the 500k-record T6 variant are deliberate stress points above typical benchmark inputs, while still within the 1–5 GiB memory of hosted interpreters.
- **Library load dominates small analyses (Inference):** with 10–12-line solutions on small files, importing pandas, matplotlib, or scikit-learn likely outweighs the analysis itself. Tier B tasks must report import time separately, and the Tier A twins show what the same analysis costs without heavy libraries.
- **Agents mostly analyze, rarely model (Inference):** ML is 7.4% of DABench concepts and 20% of DA-Code; summary statistics, correlation, distributions, and cleaning are the core.

### Gaps
- No public study of real ChatGPT Advanced Data Analysis or Claude analysis sessions gives task or file-size distributions; practitioner guides describe CSV/Excel/JSON uploads, cleaning, charts, and statistical tests (anecdotal; for example [DataCamp](https://www.datacamp.com/tutorial/how-to-use-chat-gpt-code-interpreter)).

## 8. Other recurring workloads: what are they, and how frequent is each?

### Takeaway
Utility workloads show up in a few percent of tasks each (dates 9.8%, regex 12.2%, hashing/encoding 3–4%, compression ~2% of BigCodeBench tasks), while session-level behaviors (persistent REPL state, idle waiting, snapshot/resume, timeouts, output caps) are built into every hosted platform and therefore apply to most sessions.

### Cited Findings
- **HTML-to-text and scraping:** dynamic filtering is on by default for Claude's current web search and fetch tools and uses code execution to keep only relevant content ([web fetch docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool); [Claude blog](https://claude.com/blog/improved-web-search-with-dynamic-filtering)); just-bash ships an `html-to-markdown` command ([just-bash](https://raw.githubusercontent.com/vercel-labs/just-bash/main/packages/just-bash/README.md)); BigCodeBench bs4 1.2%, requests 3.5% (Computed).
- **Regex and text search over many files:** grep, head, tail, sed, and rg dominate agent shell use ([TraceLab](https://tracelab.cs.washington.edu/exp/tool_calls/bash_command_breakdown/)); BigCodeBench `re` 12.2%, `string` 5.0% (Computed).
- **Virtual filesystem manipulation:** Manus treats the file system as "the ultimate context" and keeps a `todo.md` ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)); Anthropic recommends writing intermediate results and skills to files ([Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)); `@cloudflare/shell` provides a durable virtual filesystem (SQLite plus R2) with rollback on failed batch writes ([Cloudflare](https://blog.cloudflare.com/dynamic-workers)); just-bash offers InMemoryFs, OverlayFs (1 GiB default `maxMemoryBytes`), ReadWriteFs (100 MB copy-on-write default), and MountableFs (same README).
- **Encoding, crypto, compression:** BigCodeBench hashlib 3.0%, base64 2.5%, binascii 1.1%, zipfile 1.1%, gzip 0.4%, hmac 0.3%, cryptography 0.4% (Computed); Monty's stdlib includes base64, binascii, and hashlib ([Monty limitations](https://pydantic.dev/docs/monty/limitations/)); just-bash includes base64, md5sum, sha1sum, sha256sum, gzip, and tar ([just-bash](https://raw.githubusercontent.com/vercel-labs/just-bash/main/packages/just-bash/README.md)).
- **Date/time parsing:** BigCodeBench datetime 6.5%, time 2.8%, pytz 1.5%, dateutil 1.0% (Computed); Monty includes datetime and time (same Monty page).
- **Schema validation and templating:** I found no frequency data. Tool schemas exist on the host side (codemode declarations), and Monty supports `@dataclass` with only `eq=` and `frozen=` ([Monty limitations](https://pydantic.dev/docs/monty/limitations/)).
- **Code parsing, diffing, patching:** Claude's code execution text editor returns `str_replace` results as diffs ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool)); Codex `apply_patch` bodies appear in agent traces ([TraceLab](https://tracelab.cs.washington.edu/exp/tool_calls/bash_command_breakdown/)); BigCodeBench difflib 0.4%, ast 0.7% (Computed); Dynamic Workers' example plans and atomically applies multiple file edits ([Cloudflare](https://blog.cloudflare.com/dynamic-workers)).
- **Math and statistics:** DABench summary statistics 35% and correlation 28% ([DABench](https://arxiv.org/html/2401.05507v3)); BigCodeBench math 3.5%, statistics 1.7%, scipy 7.5% (Computed); Claude preinstalls sympy and mpmath ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool)).
- **Document parsing:** see sections 6 and 7; a 500 kB PDF is about 125,000 tokens if loaded unfiltered ([web fetch docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool)).
- **Embedding/vector similarity:** no source found.
- **PII redaction:** the MCP client can tokenize emails and phone numbers into placeholders such as `[EMAIL_1]` and restore them during tool calls ([Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)).
- **LLM calls inside scripts:** RLMs keep a long prompt in a Python REPL and let the model call sub-models over chunks; dspy.RLM injects `llm_query(prompt)` and `llm_query_batched(prompts)` with a `max_llm_calls` bound ([arXiv 2512.24601](https://arxiv.org/abs/2512.24601); [DSPy RLM](https://dspy.ai/diving-deeper/rlm/); via search summaries). smolagents' snippet-sandbox mode cannot run managed sub-agents because credentials are not passed into the sandbox ([smolagents](https://huggingface.co/docs/smolagents/tutorials/secure_code_execution)).
- **Long-lived REPL sessions:** Claude's `code_execution_20260120` keeps Python interpreter state across requests that reuse a container; containers checkpoint after about 5 minutes of inactivity and expire after 30 days ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool)); OpenAI containers expire after 20 minutes idle ([OpenAI docs](https://developers.openai.com/api/docs/guides/tools-code-interpreter)); Monty sessions keep the REPL state between commands ([Monty docs](https://pydantic.dev/docs/monty/)).
- **Idle sessions waiting on slow tools:** a pending programmatic tool call times out after about 4 minutes ([PTC docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)); Monty says snapshots make long external calls and human-in-the-loop workflows "cheap" ([Monty docs](https://pydantic.dev/docs/monty/)).
- **Snapshot/resume:** Monty can "dump the whole sandbox state to bytes at an external function call or at the end of a repl snippet" ([Monty docs](https://pydantic.dev/docs/monty/)); Blaxel VMs start from hibernation in under 25 ms while keeping memory state (vendor claim in [smolagents docs](https://huggingface.co/docs/smolagents/tutorials/secure_code_execution)).
- **Cancellation and timeouts:** PTC REPL cells have a 90-second wall-clock limit ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool)); just-bash has `maxExecutionTimeMs` and `AbortSignal` cancellation, and Node worker `resourceLimits` do not reliably cap WASM memory ([just-bash](https://raw.githubusercontent.com/vercel-labs/just-bash/main/packages/just-bash/README.md)); Monty enforces memory and time limits in the VM, so `'x' * 10**12` raises `MemoryError` before allocating ([Monty docs](https://pydantic.dev/docs/monty/)); Workers CPU time defaults to 30 s per request ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)).
- **Streaming progress:** Claude uses `echo` in 25.4% of its shell invocations as a progress-print idiom, about 2.3 echoes per echo-using command ([TraceLab](https://tracelab.cs.washington.edu/exp/tool_calls/bash_command_breakdown/)); codemode truncates final output near 6,000 tokens ([Cloudflare docs](https://developers.cloudflare.com/agents/model-context-protocol/codemode/)).

### Inferences
- **Utility compute is where interpreters diverge (Inference):** hashing, compression, date parsing, and regex are native-backed in CPython, V8, and Rust but may be interpreted in AST-walking sandboxes, so T20–T23 can show 10–100× spreads even though each is rare.
- **Sessions are where memory accumulates (Inference):** platforms bill and expire by container time (per-hour pricing, 20-minute and 5-minute idle thresholds), so per-session idle RSS (T25, T26) is likely the most important efficiency metric for hosts running many sessions.

### Gaps
- No frequency data for schema validation, templating, embedding math, PII redaction in practice, or streaming progress in code mode.
- Monty's default resource-limit values and snapshot sizes are not on the pages I read.

## 9. What do bash-centric coding agents run, and how does it overlap with scripting workloads?

### Takeaway
Shell calls are the majority of coding-agent tool calls and are dominated by search and slicing (grep, rg, sed, head, tail), followed by running Python scripts, git, and docker. They overlap with scripting on text search, JSON filtering (jq), file edits, and SQL (sqlite3), but per-command process cost and filesystem metadata speed, not interpreter speed, dominate.

### Cited Findings
- 665,453 agent steps across Claude and Codex; 423,280 shell-command calls (Claude 158,610; Codex 264,670), though another note on the page cites 335,640 calls; shell is 56.9% of tool calls and 56.6% of effective time ([TraceLab](https://tracelab.cs.washington.edu/exp/tool_calls/bash_command_breakdown/)).
- Executable shares, pooled: echo 18.1%, grep 10.1%, sed 9.1%, head 6.4%, tail 4.2%, python-script 4.2%, rg 3.0%. Claude: echo 25.4%, grep 14.3%, head 8.5%, tail 5.1%, ls 4.3%. Codex: sed 25.0%, python-script 9.6%, rg 9.6%, git 5.9%, nl 4.6%, docker 4.0%. Claude averages 5.62 executables per call (84.2% multi-executable pipelines), Codex 1.53 (same source).
- Latency: grep, ls, sed, rg, and tail run in milliseconds to tens of milliseconds; docker, pytest, and python scripts take seconds with tails of tens of seconds; Codex exec calls in this dataset are capped at 30 s (same source).
- Vercel d0 text-to-SQL agent (2025-12-22): 17 specialized tools replaced with bash over a Cube semantic layer of YAML, Markdown, and JSON files (plus an `ExecuteSQL` tool in the code sample); success 80% to 100% (5 cases), average time 274.8 s to 77.4 s, tokens ~102k to ~61k, steps ~12 to ~7; commands grep, cat, ls, find; runs in Vercel Sandbox ([Vercel](https://vercel.com/blog/we-removed-80-percent-of-our-agents-tools)).
- Bash vs SQL eval (2026-01-22, GitHub issues/PRs data): SQL 100% accuracy, 155,531 tokens, $0.51, 45 s; bash 52.7%, 1,062,031 tokens, $3.34, 401 s; filesystem tools 63.0%, 1,275,871 tokens, $3.89, 126 s; bash chained find, grep, jq, awk, xargs; `stat()` across 68,000 files made millisecond commands time out at 10 s until just-bash was optimized; bash plus SQLite reached 100% with about 2× SQL's tokens ([Vercel/Braintrust](https://vercel.com/blog/testing-if-bash-is-all-you-need)).
- just-bash: a TypeScript-simulated bash with a virtual filesystem and no VM isolation; commands include grep/rg/sed/awk/jq/sqlite3/xan/yq/curl/html-to-markdown/gzip/tar and optional python3 (CPython WASM) and js-exec (QuickJS); bounded `normal` and `hardened` profiles ([just-bash](https://raw.githubusercontent.com/vercel-labs/just-bash/main/packages/just-bash/README.md)).
- Claude's code execution tool runs both Bash and Python and edits files with `str_replace` ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool)).

### Inferences
- **Overlap map (Inference):** grep/rg/head/tail ↔ T17; jq ↔ T6 and T5; awk/sort/uniq ↔ T15 and T19; sqlite3 ↔ T37; sed/heredoc edits and `apply_patch` ↔ T18; python-script ↔ every Tier A/B task. T38 runs the overlap in both real and emulated shells.
- **Different cost structure (Inference):** in a real shell each pipeline stage is a process (fork/exec), so Claude's ~5.6 executables per call multiply process startup; in an emulated shell, commands are in-process functions and filesystem metadata speed dominates (the 68,000-file `stat()` timeouts).
- **Correctness, not only efficiency (Inference):** the bash agent's 52.7% vs SQL's 100% accuracy suggests reporting task success alongside cost when agents choose the tool.

### Gaps
- The TraceLab page does not identify the models, benchmarks, or dates behind its traces.
- A Terminal-Bench study's command shares (cat heredoc writes ~29%, Python ~21%, sed ~2%) surfaced only in a search summary of [arXiv 2606.03461](https://arxiv.org/abs/2606.03461); I could not verify them from the abstract, so they are excluded from the findings.

## 10. Which cost dominates for each workload: startup, host-call overhead, payload marshaling, compute, or memory held while waiting?

### Takeaway
With real network latency (tens to hundreds of ms per call, seconds for LLM calls), in-runtime per-call overhead is small relative to wall time, so code-mode efficiency differences come from fixed per-session memory and startup, memory per pending call and per idle session, and marshaling cost per byte. Compute-bound workloads (data analysis, utilities, text search) instead separate runtimes by interpreter and library speed.

### Cited Findings
- Startup and footprint ranges: Monty 0.80 ms (pooled) vs WASI 16 ms, Docker 195 ms, a sandbox service 1,500 ms, and Pyodide-in-Deno 2,700 ms (vendor table, [Monty docs](https://pydantic.dev/docs/monty/)); isolates "a few milliseconds" and "a few megabytes" vs containers' hundreds of ms and hundreds of MB, and Python and WebAssembly "load and run more slowly for small snippets" than JavaScript in Dynamic Workers (vendor claim, [Cloudflare](https://blog.cloudflare.com/dynamic-workers)).
- Memory ceilings: Workers 128 MB per isolate ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)); Claude containers 5 GiB RAM and 1 CPU ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool)); OpenAI containers 1 to 64 GB tiers ([OpenAI docs](https://developers.openai.com/api/docs/guides/tools-code-interpreter)); just-bash QuickJS 64 MB and OverlayFs 1 GiB defaults ([just-bash](https://raw.githubusercontent.com/vercel-labs/just-bash/main/packages/just-bash/README.md)); the smolagents Docker example uses `mem_limit="512m"` and `pids_limit=100` ([smolagents](https://huggingface.co/docs/smolagents/tutorials/secure_code_execution)).
- Billing by session time: $0.05 per container-hour beyond 1,550 free hours ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool)); $0.002 per unique Dynamic Worker loaded per day plus CPU and invocations ([Cloudflare](https://blog.cloudflare.com/dynamic-workers)).
- Network and inference latency: measured TTFB 27–574 ms (section 5); inference passes take hundreds of ms to seconds ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)).
- Payload sizes crossing the boundary: 434 KB for one 100-issue GitHub page, 2.28 MB and 7.1 MB for package metadata, 5.5 MB for a CSV (Measured, section 5); ~200 KB in Anthropic's budget example ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)).
- Filesystem metadata can dominate: 68,000-file `stat()` calls caused 10 s timeouts ([Vercel/Braintrust](https://vercel.com/blog/testing-if-bash-is-all-you-need)).
- Small sequential workloads can cost more under code mode (+8% on τ²-bench) because container and script overhead exceed the savings ([PTC docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)).

### Inferences
**Cost model (Inference):** session cost ≈ startup + binding setup(C) + Σ per call (boundary crossing + marshal(payload)) + compute; memory ≈ base + bindings(C) + live data + pending calls × per-pending memory + retained session state × idle time.

| Workload (tasks) | Dominant cost | Secondary | Primary metric to report |
|---|---|---|---|
| Single small call (T1) | Startup | Binding setup | Session create time; RSS per session at K = 1000 |
| Serial chain at L0 (T2, M2) | Host-call overhead | Marshaling | µs and CPU per call (slope) |
| Serial chain at real latency (T2 M3, T5, T9) | Memory held while waiting | Timers | RSS per waiting session × wall time |
| Parallel fan-out (T3, T4, T8) | Memory per pending call | Scheduler CPU when results land | RSS vs N slope; CPU per call; connection-cap queueing |
| Large result filter (T6, T11) | Marshaling (parse/materialize) | Peak memory | ms per MB; peak RSS / payload ratio; string vs structured |
| Catalog scaling (T10) | Binding setup and type declarations | Per-session duplication of bindings | Startup and RSS vs C; shared vs per-session cost |
| Web extraction (T12–T14) | Memory held while waiting | Decompression and parse CPU | Per-path (host vs embedded) CPU and RSS |
| Data analysis (T15, T16, T32) | Compute | Library load; dataframe memory | CPU-seconds; import time; peak RSS |
| Text search (T17–T19, T38) | FS metadata and read I/O | Regex CPU; process spawn in real shells | Files per second; MB/s scanned |
| Charts and documents (T30, T31, T33–T35) | Library load and serialization compute | Output transfer | Import time; render time; artifact bytes |
| Sessions and idle (T25, T26) | Memory held while idle | Snapshot and restore | Idle RSS per session; snapshot bytes and time |
| Utilities (T20–T24) | Compute | None | Throughput vs native baseline |
| Sub-LLM (T27) | Memory held while waiting | Prompt marshaling | RSS during multi-second waits |
| Limits and output (T28, T29) | Kill latency; stdout capture | Memory reclamation | Time-to-kill; post-kill RSS; capture overhead per byte |

- **Which runtimes the metrics favor (Inference):** pooled interpreters and isolates win the startup- and idle-dominated rows; JIT engines and native-library interpreters win compute rows; structured marshaling avoids double parsing but may copy more for large values, which T6's two modes isolate.
- **Shared vs per-session cost (Inference):** a runtime that compiles tool declarations once and shares them (snapshots, shared code pages) amortizes C across sessions; the benchmark must report T10 at K = 100 to expose whether catalog cost is per session.

### Gaps
- No public measurements of per-pending-call memory, per-idle-session memory, or marshaling cost per MB for any code-mode runtime; vendor numbers are startup and footprint only.
- No public data on library import times (pandas, matplotlib) inside hosted interpreters; T32 and T33 measure them directly.
