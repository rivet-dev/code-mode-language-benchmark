# JavaScript/TypeScript engines and platforms for untrusted, LLM-generated code (as of 2026-11-13)

Scope: every JS/TS execution option found, classified as **Group B** (the runtime itself is a credible in-process boundary), **B-conditional** (capability-limited but weakly hardened, or missing limits), or **Group A** (needs OS/VM isolation). Host languages of interest: Rust and Node.js/TypeScript.

Conventions used throughout:
- "Vendor claim" marks numbers published by the product's maker without a stated method. "Stale" marks data older than 2024.
- **zoo** = ivankra/javascript-zoo data file (https://zoo.js.org/engines.json, engine builds dated roughly 2026-02 to 2026-03). The zoo runs the V8 benchmark suite (Octane-style tests; higher score = faster). I computed the **core-8 geomean** myself from the per-test scores (Richards, DeltaBlue, Crypto, RayTrace, EarleyBoyer, RegExp, Splay, NavierStokes; amd64; default build). The zoo README names neither the machine nor the run date. These are CPU-bound tests; short, I/O-bound code-mode scripts depend far less on JIT speed.
- **Local measurement** = numbers I measured on 2026-11-13 on a shared dev host (AMD EPYC 7443P, 24C/48T, 54 GB RAM, Linux 6.12). The host was heavily loaded (load average 40 to 69), so **timings are inflated and are only useful as ratios within one run**. Memory numbers are less affected. Versions: Node v22.23.1 (V8 12.4), Deno 2.5.2 (V8 14.0), Bun 1.3.14, isolated-vm 6.2.0, quickjs-emscripten 0.32.0 (it bundles Bellard QuickJS 2025-09-13, 32-bit Wasm). Methods are summarized in the "Local measurement method" subsection.

## Catalog overview: which JS/TS execution options exist, how they classify, and which are worth benchmarking

### Takeaway
Only three families combine an in-process boundary with enforceable memory and CPU limits and real production use for hostile code: **V8 isolates** (Cloudflare Workers and Dynamic Workers, rusty_v8/deno_core, isolated-vm), **any engine compiled to WebAssembly** (QuickJS via quickjs-emscripten, Javy or Hako; SpiderMonkey via StarlingMonkey), and **hardware micro-VMs** (hyperlight-js). Native QuickJS/quickjs-ng (rquickjs), Boa, Goja, Hermes, XS and the Rust/Zig newcomers are **B-conditional**. Node, Bun, Deno CLI, LLRT and txiki.js are **Group A**. vm2, `node:vm` and SandboxJS are **not boundaries**: they had dozens of escapes in 2026.

#### Local measurement method
- Pending-await cost: create 200,000 async functions that each await a pending Promise, force GC twice, divide the `heapUsed` delta by N. Node used `--expose-gc`; Deno used `--v8-flags=--expose-gc`. (measured locally)
- isolated-vm: create 100 isolates (each `memoryLimit: 128` with one context and `evalSync("1+1")`), then 500 contexts in one isolate; record the RSS delta after GC and wall time. Then 20,000 guest async functions each await a host Promise through `Reference.apply(..., {result:{promise:true}})`; resolve them all; time a 100,000-iteration sync `Callback` loop. (measured locally)
- quickjs-emscripten: the same pattern with 500 runtimes, 1,000 contexts, 20,000 pending `newPromise` handles, a 100,000-call sync host function loop, and 20 asyncify modules. (measured locally)

### Inferences
- Suggested benchmark set, about 10, covering both host languages and all three isolation styles: (1) rusty_v8/deno_core isolates and contexts, jit vs jitless, with a startup snapshot; (2) isolated-vm on Node; (3) self-hosted workerd plus Dynamic Workers as the hosted reference; (4) quickjs-ng native via rquickjs; (5) QuickJS-in-Wasm under wasmtime from Rust (Javy-style), and QuickJS-in-Wasm in Node (quickjs-emscripten sync and asyncify, plus Hako if its host story fits); (6) StarlingMonkey under wasmtime; (7) Boa as the pure-Rust native option; (8) hyperlight-js as the micro-VM option; (9) Group A baselines: Deno and Node subprocesses (plus Bun and LLRT for idle RSS and startup); (10) optionally GraalJS UNTRUSTED for reference only, since it has no Rust or Node host story.
- agentOS already uses V8 isolates and Wasm in one process. Results 1 to 6 map directly onto its two existing mechanisms: "QuickJS in Wasm" is the closest analog to its Pyodide-in-Wasm Python path.

### Gaps
- The zoo does not publish its benchmark machine or run date. Data is current only to about 2026-03, so QuickJS 2026-06-04 and Boa 0.22 are not reflected.
- No per-instance memory numbers were found for native quickjs-ng, Boa, Nova, Hermes, StarlingMonkey or hyperlight-js. They need to be measured.
- The web-search budget ran out partway through. Later facts came from direct fetches, the GitHub, crates.io, npm and NVD APIs, and local measurement. No HN discussions or third-party benchmark posts beyond those listed were consulted.

## V8 isolates: footprint, creation time, jitless/pointer compression/V8 sandbox, async host calls, pending-await cost, isolated-vm status

### Takeaway
A V8 isolate costs about **1.1 MB RSS and about 3 ms** to create from V8's built-in snapshot. A **new context inside an existing isolate costs about 160 KB and under 1 ms**. Shared-isolate designs report **0.35 to 0.47 MB per tenant** (celld, vendor). A suspended `await` on a pending host Promise costs about **0.4 to 0.8 KB** of guest heap. Async host calls never block a host thread in deno_core, workerd or isolated-vm. **jitless** costs about 18x on CPU-bound code but removes runtime code generation and Wasm. **Pointer compression** roughly halves heap size. The **V8 sandbox** costs about 1% but needs per-isolate-group cages to scale. The **2026 attacks** on workerd show that native bindings ("glue") and Spectre are major weak points alongside V8 itself. isolated-vm is in **maintenance mode** and had a critical guest-reachable escape in 2026-08.

### Cited Findings

#### V8 engine-level facts
- **jitless** (V8 7.4, 2019, stale): about 40% slower on Speedometer 2.0 and about 80% slower on the Web Tooling Benchmark; about 6% slower on a YouTube TV browsing simulation. No runtime allocation of executable memory; regexps are interpreted; "WebAssembly is currently unsupported". Median heap change only −1.7%. Motivation: platforms that forbid writable+executable memory, and a smaller attack surface. ([v8.dev/blog/jitless](https://v8.dev/blog/jitless))
- zoo (2026-03 builds): V8 jitless scores 2,614 vs 47,285 with JIT on core-8 (about 18x), and 3,880 vs 58,012 on all 17 tests (about 15x). The jitless `d8` binary is 13 MB vs 21 MB. ([zoo data](https://zoo.js.org/engines.json))
- **Lite mode** (2019, stale): disables TurboFan and feedback vector allocation and ages bytecode; **22% average heap reduction** (up to 32%), about 1.8 MB on an AndroidGo device. ([v8.dev/blog/v8-lite](https://v8.dev/blog/v8-lite))
- **Wasm without JIT**: a V8 developer said in a May 2024 thread that Microsoft was upstreaming its Wasm interpreter "DrumBrake". GrapheneOS's Vanadium enables DrumBrake to provide Wasm without JIT, and notes that not all Wasm features are supported. ([chromium-dev thread](https://groups.google.com/a/chromium.org/g/chromium-dev/c/HDVGsHrhWCY), [GrapheneOS forum](https://discuss.grapheneos.org/d/35061-offensivecon-drumbrake-adds-massive-attack-surface-applies-to-vanadium)). Upstream status as of 2026-11 is unknown.
- **Pointer compression** (2020, stale): "reduces V8 heap size up to 43%", with 32-bit offsets inside a 4 GB region. ([v8.dev/blog/pointer-compression](https://v8.dev/blog/pointer-compression))
- Node does not enable pointer compression by default. Enabling it forces every isolate in the process (main thread and workers) into one 4 GB cage. Platformatic's `node-caged` images (Node 25.x and 26.x) report about **50% less memory** with a **2.5% average latency overhead** (about 1 ms on a 40 ms median) on a Next.js app at 400 req/s. Add-ons built with legacy NAN do not work. These are the publisher's own benchmark numbers. ([Platformatic](https://blog.platformatic.dev/we-cut-nodejs-memory-in-half))
- **V8 sandbox** (2024-04-04): confines memory corruption to an in-heap region; "only around 1% or less" overhead on Speedometer/JetStream; reserves about 1 TB of virtual address space; a build-time flag (`v8_enable_sandbox`); enabled by default in 64-bit Chrome and part of the Chrome VRP; "not yet a strong security boundary" at that time. ([v8.dev/blog/sandbox](https://v8.dev/blog/sandbox))
- **Workers hardening** (2025-09-25, modified 2026-07-15): Before V8 changes, all isolates in a process shared **one** sandbox, which caps total heap below 4 GiB. Igalia added "isolate groups" to V8, and Workers now places **one isolate per sandbox**, each reserving 8 GiB of virtual space (4 GiB pointer-compression cage plus 4 GiB for buffers). Memory protection keys (MPK; about 12 usable keys) are assigned in strict rotation, so no two sandboxes within 32 GiB share a key. No overhead numbers were published. ([Cloudflare blog](https://blog.cloudflare.com/safe-in-the-sandbox-security-hardening-for-cloudflare-workers/))
- **Spectre in 2026**: Cloudflare's own reassessment found a limitation in its Dynamic Process Isolation (DyPrIs) and demonstrated a remote Spectre attack leaking **up to 12 bit/s at 99% accuracy in production**. Coverage describes it leaking a JWT from a co-located Worker, versus 120 bits/hour in 2021. Fixes: enhanced DyPrIs, the V8 sandbox, and MPK isolation. Cloudflare states that neither the V8 sandbox nor MPK is a complete Spectre mitigation. ([Cloudflare blog](https://blog.cloudflare.com/revisiting-spectre-attacks-on-workers/), [The Hacker News](https://thehackernews.com/2026/08/cloudflare-workers-spectre-attack-leaks.html))
- **Native glue bugs in 2026**: Check Point (2026-08-07, Black Hat USA 2026) found memory-corruption bugs in workerd's C++ bindings: a URLPattern out-of-bounds read, a zlib `deflateParams()` use-after-free, an HTMLRewriter use-after-free, and a KV SQL authorizer bypass. Two were rated Critical. The researchers chained a prompt injection into a **Code Mode escape that ran shellcode**, but only against a self-hosted build **with the V8 sandbox disabled**. Cross-tenant secret reads were shown on self-hosted workerd. Production was fixed, and self-hosters should run workerd ≥ v1.20260619.1. Conclusions: "The engine is not the whole boundary" and "Prompt injection is a code-execution entry point." No CVEs were assigned. ([Check Point Research](https://research.checkpoint.com/2026/when-agentic-glue-melts/))

#### Measured footprint and host-call costs
- **Pending await (V8)**: an async function suspended on a shared pending Promise retains **~408 B** (Node 22.23.1, V8 12.4) and **~400 B** (Deno 2.5.2, V8 14.0). Awaiting its own Promise whose resolver is held by the host costs **~586 B / ~578 B**. A bare pending Promise plus its resolver is ~173 B. A JavaScriptCore (Bun) run gave 250 B for the first case, but its other cases read 0, so the JSC numbers are unreliable. (measured locally)
- **isolated-vm 6.2.0 on Node 22.23.1**: a new isolate plus one context plus a trivial eval costs **3.1 ms and ~1.15 MB RSS**, with 570 KB of used heap per isolate. A new context inside an existing isolate costs **0.66 ms and ~160 KB RSS**. A guest async function awaiting a host Promise via `Reference.apply` retains **~782 B** of guest heap. Resolving 20,000 host Promises and running their guest continuations took 76.6 ms (**~3.8 µs each**). A sync `Callback` round trip takes **1.38 µs**. A `Callback({async:true})` whose host function returned a Promise failed with "#<Promise> could not be cloned"; promise proxying needed `Reference.apply` with `result: {promise: true}`. (measured locally, under heavy host load)
- Vendor and older numbers: "Isolates start in 5 milliseconds"; a basic Node Lambda uses 35 MB, while with a shared runtime "that drops to around 3 MB" (2018, stale) ([Cloudflare 2018](https://blog.cloudflare.com/cloud-computing-without-containers/)). Isolates start "around a hundred times faster than a Node process" and use about an order of magnitude less memory, with no MB figure given ([How Workers works](https://developers.cloudflare.com/workers/reference/how-workers-works/)). Custom startup snapshots cut **context** creation from 40 ms to under 2 ms (2015, stale) ([v8.dev](https://v8.dev/blog/custom-startup-snapshots)). The snapshot size sets the per-isolate heap floor ([v8.dev lazy deserialization](https://v8.dev/blog/lazy-deserialization)).
- **celld** (Deno's self-hosted Durable Objects, 2026): v0.2.0 introduced "shared isolates (~471 KB/cell)". Ryan Dahl later reported per-cell memory going from "500k to 350k" (v0.5.0), and celld.dev states 0.47 MB per cell and 2,500 cells per 8 GB. These are vendor claims. ### Inferences
- For code mode, a per-session **context** in a shared per-tenant isolate (~160 KB, <1 ms) is about 7x cheaper than a fresh isolate (~1.1 MB, ~3 ms). Contexts in one isolate are not isolated from each other's CPU time or heap OOM, though. Use a fresh isolate per tenant and a context per session.
- A guest awaiting 100 slow host calls costs roughly 40 to 80 KB of guest heap in V8, plus host-side future state. Memory per idle-but-waiting session is dominated by the isolate or context baseline, not by the pending awaits.
- jitless is probably the right default for short code-mode scripts: it removes JIT bugs (a large V8 bug class) and runtime code generation. It costs about 15 to 18x on compute loops, which matters only for heavy data processing. It also disables Wasm unless DrumBrake is built in.
- The 2026 workerd findings apply directly to agentOS: every native binding exposed to guest JS (compression, parsers, KV, URL) is part of the boundary and needs its own fuzzing and review.

### Gaps
- No published, controlled per-isolate RSS or creation-time numbers for rusty_v8/deno_core with and without a custom startup snapshot, with pointer compression, or with the V8 sandbox. Whether `rusty_v8` builds enable the V8 sandbox or pointer compression by default was not verified.
- Dynamic Workers memory per isolate is not documented (the 128 MB Workers limit is assumed to apply). Network access with no `globalOutbound` set appears to be open, but the docs are ambiguous.
- No V8 CVE count for 2025 to 2026 was compiled.

## QuickJS family: Bellard QuickJS, quickjs-ng, MicroQuickJS, rquickjs, quickjs-emscripten, Javy, LLRT, txiki.js, Figma

### Takeaway
QuickJS is the default "small, safe-ish interpreter": about 1 MB binary, under 300 µs per runtime lifecycle (vendor), **~94 KB per runtime+context in Wasm (measured)**, memory limits and interrupt handlers, and roughly 40% of V8-jitless speed (zoo; the 2026-06 release claims +42%). It is a C engine with a **steady stream of memory-safety CVEs** (seven CVSS 6.5 to 8.8 in October 2025 alone, and a critical quickjs-ng RCE in 2026-05). Native embedding is therefore **B-conditional**, while QuickJS **compiled to Wasm** (quickjs-emscripten, Javy, Hako) or inside a micro-VM (hyperlight-js) is **B**. LLRT and txiki.js are full runtimes with ambient I/O (**Group A**).

### Cited Findings

#### Engines
- **Bellard QuickJS**: MIT; releases 2025-04-26 (bignum extensions and qjscalc removed), 2025-09-13, and **2026-06-04** ("about 42% faster than the previous one" on bench-v8). 1. **What**: Microsoft-originated, Apache-2.0, crate 0.5.0 (2026-11-05); 16 GitHub stars, so very early. ([hyperlight-js](https://github.com/hyperlight-dev/hyperlight-js), [crates.io](https://crates.io/crates/hyperlight-js))
2. **Group**: **B** (hardware virtualization per sandbox; no guest OS). Maturity is the risk.
3. **Embedding**: a Rust crate (`SandboxBuilder`) and Node.js bindings ("JS Host API" with user modules and host functions). Requires KVM or MSHV on Linux x86_64, KVM on aarch64, WHP on Windows, or Hypervisor.framework on macOS aarch64. ([README](https://github.com/hyperlight-dev/hyperlight-js))
4. **Limits**: guest scratch budget, default and minimum 5 MiB (heap, stack, transport pools, page tables, CoW pages); "Execution Monitors" for timeouts. Guest OOM poisons the sandbox, which must be restored from a snapshot or rebuilt. ([README](https://github.com/hyperlight-dev/hyperlight-js))
5. **Async**: not documented (gap).
6. **HTTP**: not documented; presumably host functions only (inference).
7. **Footprint**: at least 5 MiB scratch per sandbox; no startup numbers published (gap).
8. **Speed**: QuickJS tier plus VM-exit cost per host call (inference).
9. **Snapshot**: **persistent snapshots across processes** are supported ([README](https://github.com/hyperlight-dev/hyperlight-js)).
10. to 11. Ecosystem: QuickJS. No users listed.

#### Record: AWS LLRT (Group A)
- v0.10.0-beta (2026-11-05); "an experimental package … intended only for evaluation purposes"; QuickJS in Rust with no JIT; claims "up to over **10x** faster startup" on Lambda (vendor; charts compare Node 20 at 128 MB ARM). TypeScript must be transpiled ahead of time. Partial `node:fs`, `node:child_process`, `net` and `crypto`; no `vm` or `worker_threads`. `LLRT_NET_ALLOW` is a deny-by-default host allowlist (an empty list blocks everything) and `LLRT_NET_DENY` takes precedence; both cover `fetch` and `node:net`/`dgram`. GC threshold defaults to 20 MB (`LLRT_GC_THRESHOLD_MB`). No sandboxing claims. ([LLRT README](https://github.com/awslabs/llrt), [releases](https://github.com/awslabs/llrt/releases)) **Group A**, because file and process APIs are ambient.

#### Record: txiki.js (Group A)
- v26.11.0 (2026-11-01), MIT; quickjs-ng plus libuv; `fetch`, WebSocket, TCP/UDP/Unix sockets, HTTP server, file I/O, child processes, signals, `tjs:ffi`, `tjs:sqlite`, Web Workers, and standalone executables (`tjs compile`). #### Figma plugin sandbox (stale, 2019)
- Figma first used the Realms shim. After a privately disclosed Realms-shim vulnerability, it switched to "a JavaScript VM written in C" compiled to WebAssembly, accepting that "It's slower than regular JavaScript since this interpreter is not a JIT". Plugin code reaches the outside only through whitelisted APIs and opaque handles. The page does not state current status. ([Figma blog, 2019](https://www.figma.com/blog/how-we-built-the-figma-plugin-system/)) The `ses` advisory GHSA-6jg8-7333-554w records the 2019 "Sandbox Breakout in realms-shim" ([GitHub advisory](https://github.com/advisories/GHSA-6jg8-7333-554w)).

### Inferences
- For a Rust host, **QuickJS-in-Wasm under wasmtime** (Javy-style) is likely the best B-group alternative to V8. It contains engine CVEs and gets a ~94 KB to ~1 MB per-session cost, but it pays about 0.65x native QuickJS speed and needs an async host-call design (JSPI is not available in wasmtime; use Promise-returning imports and a job pump).
- In Node hosts, quickjs-emscripten's **8.6 µs per sync host call** will dominate code-mode workloads that make thousands of small tool calls. Benchmark host-call throughput, not only creation cost.
- Asyncify's "one suspended call at a time" rule rules out the parallel `Promise.all` tool-call pattern unless you use the Promise-based API. Use `newPromise` rather than asyncify for code mode.

### Gaps
- No native per-instance RSS measurements for quickjs-ng/rquickjs or Bellard QuickJS.
- Shopify's numeric instruction limit was not on the fetched page.
- Whether Figma still uses a QuickJS-Wasm sandbox in 2026 is unknown.
- No JSPI-based QuickJS variant was found for Node; Wasmer's SDK uses JSPI internally (internal notes `~/.agents/research/wasmer-launch-week-2026-08-31.md`).

## Other embeddable or sandboxable engines: Boa, Nova, Kiesel, Brimstone, Hermes, JerryScript, Duktape, Elk, Escargot, Goja/Otto, GraalJS, SpiderMonkey-in-Wasm, Porffor, engine262, Andromeda, XS

### Takeaway
Outside V8 and QuickJS, only **StarlingMonkey/ComponentizeJS** (SpiderMonkey in Wasm; production at Fastly and Fermyon) and **GraalJS with `SandboxPolicy.UNTRUSTED`** (JVM only) are credible boundaries with limits. **Boa** is the most mature pure-Rust engine (95.6% test262, v0.22) but is about 5x slower than QuickJS and has **no heap cap or general interrupt**, so it is B-conditional. Nova reached 1.0 (~80% test262), and Brimstone (>97%) and Kiesel are not production-ready. Hermes, Escargot, JerryScript, Duktape, Elk and mquickjs target embedded or mobile and make no sandbox claims. **XS/xsnap** is notable for metering plus resumable heap snapshots. Porffor (AOT) and engine262 are research-grade.

## In-realm isolation: SES/Hardened JS, LavaMoat, ShadowRealm, `node:vm`, vm2, SandboxJS

### Takeaway
None of these is a CPU or memory boundary. **`node:vm`** says so explicitly. **vm2** was revived and is "actively maintained", but it had **13 escape CVEs from January to May 2026 and another wave in October 2026**. **SandboxJS** had nine critical escape advisories in February to May 2026. **SES/Hardened JS** is an integrity mechanism with a credible design and real users (MetaMask Snaps, Agoric, LavaMoat), but it does not limit infinite loops or memory and has had high and critical CVEs. **ShadowRealm** is still Stage 2.7 and unshipped. Treat all of them as defense in depth inside a real boundary.

### Cited Findings
- `node:vm`: "**The `node:vm` module is not a security mechanism. Do not use it to run untrusted code.**" By default, `timeout` does not cover microtasks unless `microtaskMode: 'afterEvaluate'`. ([Node vm docs](https://nodejs.org/api/vm.html))
- **vm2**: README "Important Security Disclaimer": "researchers and security professionals continuously discover new ways to escape the vm2 sandbox". The status table says Node.js "Supported. The sandbox is a security boundary" but Bun is "Experimental … **not** a security boundary". The project is "Actively maintained with patches for known escape methods". Latest version 3.12.2 (2026-09-08). ([vm2 README](https://github.com/patriksimek/vm2), [npm](https://www.npmjs.com/package/vm2))
- vm2 2026 CVEs: CVE-2026-22709 (Jan; fixed 3.10.2); CVE-2026-24118, -24120, -24781, -26332, -26956 (May 4); CVE-2026-43997, -43999, -44005 through -44009 (May 7; fixed by 3.11.2). Many score 9.0 to 10.0. ([Kodem](https://www.kodemsecurity.com/resources/vm2-sandbox-escape-vulnerabilities-the-2026-cve-wave-turning-ai-agents-into-host-rce-vectors)) A further wave on 2026-10-05/07 includes critical CVE-2026-93605, -92955 (NodeVM escape), -92934 (host-wrapped AggregateError to RCE) and -92953, plus a `timeout` bypass via FinalizationRegistry (CVE-2026-92942) ([GitHub advisory DB](https://github.com/advisories/GHSA-pq68-rvw4-xp4r), [GHSA-x965-fc75-jpqh](https://github.com/advisories/GHSA-x965-fc75-jpqh)).
- **SandboxJS** (`@nyariv/sandboxjs`, a JS-in-JS interpreter with prototype whitelisting): critical escapes CVE-2026-25142, -25520, -25586, -25587, -25641, -25881, -26954, -34208 and -43898 (Feb to May 2026), plus an execution-quota bypass (CVE-2026-32723) and a parser stack-overflow DoS. ([GitHub advisory DB](https://github.com/advisories/GHSA-g8f2-4f4f-5jqw), [SandboxJS](https://github.com/nyariv/SandboxJS))
- **n8n** (workflow automation) fixed an "Expression Sandbox Escape via Shared Builtin Tampering and Code-Printer Injection Leads to Code Execution" (GHSA-6xcw-7xm6-48c6, high, 2026-09-10). It shows the in-realm failure mode in a production product. ([GitHub advisory](https://github.com/advisories/GHSA-6xcw-7xm6-48c6))
- **SES / Hardened JavaScript**: "improves a program's integrity in the face of adversarial code in the same Realm"; Compartments are "a sandbox in which a program … can execute but not escape"; lockdown removes `Date.now()`/`Math.random()` timing sources. However, "Any party in the same agent … can drop into an infinite loop and prevent all other parties from making progress"; it recommends process or worker boundaries for availability. Users: Agoric, Moddable, MetaMask (LavaMoat), MetaMask Snaps. Implementations: the `ses` shim and native XS. ([hardenedjs.org](https://hardenedjs.org/)) `ses` 2.3.0 (2026-08-13) ([npm](https://www.npmjs.com/package/ses)). CVEs: CVE-2025-32792 (high, 2025-04-18: global contour bindings leak into Compartment scope) and CVE-2023-39532 (critical, dynamic import exfiltration) ([GHSA-h9w6-f932-gq62](https://github.com/advisories/GHSA-h9w6-f932-gq62), [GHSA-9c4h-3f7h-322r](https://github.com/advisories/GHSA-9c4h-3f7h-322r)). LavaMoat is active (webpack plugin v3.0.1, 2026-10-09; `lavamoat` 11.1.7) ([LavaMoat](https://github.com/LavaMoat/LavaMoat)).
- **ShadowRealm**: the README says "Currently at Stage 2.7"; the spec draft is dated 2025-02-10; the repo was last pushed 2025-02-10 ([proposal](https://github.com/tc39/proposal-shadowrealm), [spec draft](https://tc39.es/proposal-shadowrealm)). No reliable evidence of shipping in 2026 was found. Firefox shipped a flag-gated implementation in 2022, and one deck records a demotion from Stage 3 ([search summary of TC39 materials](https://js-proposals.vercel.app/Proposals/Stage-2.7/shadowrealm)).

### Inferences
- In code mode the model writes the script, and prompt injection makes the script adversarial. Check Point says so explicitly for Code Mode. Integrity-only mechanisms (SES, ShadowRealm) are useful for protecting the host's own objects inside a V8 isolate or Wasm guest, but not as the boundary.
- SES `lockdown()` plus `harden()` inside each isolate is cheap defense in depth against prototype-pollution-style tool-API abuse (inference; not measured).

### Gaps
- No 2026 TC39 meeting record on ShadowRealm was found (the search budget ran out).
- SES runtime overhead (lockdown cost per context) was not measured.

## Group A runtimes: Node.js, Deno, Bun (permission models, idle RSS, startup)

### Takeaway
None of the three is a boundary against hostile code. **Node's permission model** is stable but is explicitly a "seat belt" that "does not protect against malicious code". **Deno's permissions** are enforced by the runtime, but its docs ask for "more than one layer of defense" and recommend VMs or microVMs for untrusted code; there were more than 10 permission-bypass advisories in 2025 to 2026, and official runtime development ends about October 2027. **Bun has no permission model**: Node permission flags are silently ignored, and implementation PRs were still open in November 2026. Measured idle RSS: Bun ~31 to 33 MB, Node ~42 MB, Deno ~57 to 61 MB.

### Cited Findings
- **Node** permission model: "Added in: v20.0.0"; no longer experimental in v23.5.0 and v22.13.0; Stability 2. "This feature does not protect against malicious code … The permission model implements a 'seat belt' approach … Malicious code can bypass the permission model." Flags: `--permission`, `--permission-audit`, `--allow-fs-read/write`, `--allow-child-process`, `--allow-worker`, `--allow-net`, `--allow-addons`, `--allow-wasi`, `--allow-ffi`, `--allow-openssl-store`. Caveats: symlinks are followed outside granted paths; existing file descriptors bypass checks; `process._debugProcess()` is ungated. ([Node permissions](https://nodejs.org/api/permissions.html))
- Node versions: 26.13.1 (2026-11-10, LTS "Lithium", V8 14.6); 24.22.3 (LTS "Krypton", V8 13.6); 27.0.0-alpha (V8 15.6). ([Node release index](https://nodejs.org/dist/index.json))
- **Deno**: "Deno is secure by default"; "The security model is enforced by the Deno runtime"; "When executing untrusted code, it is important to have more than one layer of defense"; `--allow-run` and `--allow-ffi` should be treated "as equivalent to `--allow-all`"; recommends "a sandboxed environment like a VM or MicroVM (gVisor, Firecracker, etc)" and OS sandboxing; "All code executing on the same thread shares the same privilege level". ([Deno security docs](https://docs.deno.com/runtime/fundamentals/security/))
- Deno permission-bypass advisories: CVE-2025-48935 (SQLite `ATTACH` bypass, CVSS 9.1), CVE-2025-61785/61786 (deny-write/deny-read bypasses, fixed in 2.5.3), and in May to June 2026 CVE-2026-49859 ("`fetch()` API sandbox bypass via missing DNS resolution check"), -49860 (WebSocket), -49411 (`--deny-net` bypass via numeric hostnames), -49406 (`--allow-read` bypass via `package.json` main), -49401 (macOS Unicode normalization), -49983 (env), plus command injection CVE-2026-27190/-32260/-49402. ([Deno advisories](https://github.com/denoland/deno/security/advisories), [GitLab advisory CVE-2025-61785](https://advisories.gitlab.com/pkg/cargo/deno/CVE-2025-61785/), [cvefeed CVE-2025-48935](https://cvefeed.io/vuln/detail/CVE-2025-48935))
- Deno future: one more year of monthly bug-fix and security releases, then development ends; Deno Deploy shuts down after six months; rusty_v8 continues ([Deno blog, 2026-10-09](https://deno.com/blog/cloudflare)). Latest Deno is v2.9.8 (2026-10-21) ([releases](https://github.com/denoland/deno/releases)).
- **Bun**: PR #35779 (2026-07-25, closed unmerged): "Bun does not implement Node's permission model. Today `--permission` and every `--allow-*` flag fall through the unknown-flag skip path … the program runs with no sandbox." Implementation PRs #35403 and #35492 were still open on 2026-11-13. ([PR 35779](https://github.com/oven-sh/bun/pull/35779), [PR 35403](https://github.com/oven-sh/bun/pull/35403), [PR 35492](https://github.com/oven-sh/bun/pull/35492)) Latest Bun is 1.4.4 (2026-10-22) ([releases](https://github.com/oven-sh/bun/releases)).
- Measured (local, loaded host; median of 22 runs): hello world wall time Node v22.23.1 **66.8 ms** (`--jitless` 80.4 ms), Deno 2.5.2 **102.5 ms**, Bun 1.3.14 **63.3 ms**; max RSS Node **42.3 MB**, Deno **56.7 MB**, Bun **31.3 MB**; idle RSS after 1.5 s Node **41.9 MB**, Deno **60.7 MB**, Bun **33.1 MB**. Absolute times are inflated by load (load average ~65 on 48 threads). (measured locally)

### Inferences
- If a Group A runtime is used for agent scripts, the per-session cost floor is the process (~30 to 60 MB RSS plus sandbox overhead) versus about 1 MB for a V8 isolate or about 0.1 MB for QuickJS-in-Wasm. That is a 30x to 500x density gap before considering CPU.
- Deno's permission model is better treated as a policy layer inside a microVM or gVisor. Its 2026 network-permission bypasses (DNS rebinding-style checks in `fetch` and WebSocket) are exactly the HTTP-egress controls code mode would rely on.

### Gaps
- No independent, published 2025 to 2026 startup and idle-RSS comparison of Node 26, Deno 2.9 and Bun 1.4 was found (the search budget ran out); the local numbers use older versions under heavy load.

## TypeScript: per-script transform cost and engines that accept TS directly

### Takeaway
Type stripping costs **about 0.1 to 0.6 ms per typical 40-line agent script** once the transformer is loaded, plus **50 to 600 ms one-time load cost** per process or isolate. oxc-transform was fastest (101 µs warm, 52 ms cold). Node's built-in stripper (amaro/swc-wasm) took about 250 µs. Strip-only tools reject `enum`, runtime `namespace` and parameter properties. Engines that accept TS directly: **Deno, Node (erasable syntax only, and not under `--jitless`), Andromeda, Hako, Porffor, Hermes (partial)**, and Bun (widely documented, but not re-verified in this pass). Cloudflare Code Mode has the model write **JavaScript** against TypeScript API declarations. **TypeScript 7 (Go native)** no longer exposes the classic `transpileModule` JS API from its npm root.

### Cited Findings
- **Node**: type stripping is on by default since v23.6.0 and v22.18.0 and **Stable since v25.2.0 and v24.12.0**. It replaces types with whitespace (no source maps needed), does no type checking, and ignores `tsconfig`. **`enum`, runtime `namespace`, parameter properties and import aliases are unsupported** (`ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`), and decorators fail to parse. It "requires WebAssembly" and throws `ERR_WEBASSEMBLY_NOT_SUPPORTED` without it. `--experimental-transform-types` was removed in v26.0.0. It works for `--eval` and STDIN; files under `node_modules` are not stripped. ([Node TypeScript docs](https://nodejs.org/api/typescript.html))
- Consequence verified locally: `node --jitless file.ts` (Node v22.23.1) fails with "Error [ERR_WEBASSEMBLY_NOT_SUPPORTED]: WebAssembly is not supported in this environment, but is required for TypeScript", while the same file runs without `--jitless`. A jitless V8 host must therefore strip types in the host before handing code to the isolate. (measured locally)
- **amaro** 1.3.0 (2026-10-27) is "a Node.js wrapper around the SWC TypeScript parser and type stripper … compiled to WebAssembly", used internally for Node type stripping ([amaro](https://github.com/nodejs/amaro)). **ts-blank-space** 0.9.0 is a ~800-line pure-JS stripper built on the official TypeScript parser, "Fastest compared to non-native (JavaScript or Wasm)" (vendor claim) ([ts-blank-space](https://github.com/bloomberg/ts-blank-space)).
- Measured per-script cost (local; Node v22.23.1; a 42-line code-mode script with interfaces, generics, `as const` and `Promise.all`; cold = `require` plus first transform in a fresh process; warm = median of 2,000 runs; loaded host):

| Transformer (version) | Cold (load + 1st) | Warm median | Warm p99 | Process RSS |
|---|---|---|---|---|
| oxc-transform (0.158.0, native) | 51.6 ms | **101 µs** | 214 µs | 55 MB |
| amaro strip-only (1.3.0, swc→Wasm) | 72.6 ms | 249 µs | 1,079 µs | 80 MB |
| Node `module.stripTypeScriptTypes` (amaro inside; experimental warning on v22) | 64.4 ms | 259 µs | 861 µs | 84 MB |
| @swc/core (1.16.22, native) | 219 ms | 309 µs | 468 µs | 77 MB |
| sucrase (3.35.1, JS) | 102 ms | 536 µs | 4.3 ms | 68 MB |
| ts-blank-space (0.9.0, JS + TS parser) | 612 ms | 621 µs | 4.0 ms | 122 MB |
| esbuild `transformSync` (0.28.2; sync IPC to a Go subprocess) | 160 ms | 4.9 ms | 17 ms | 80 MB |

  (measured locally; all outputs verified free of type syntax)
- `typescript` 7.0.2 (2026-07-08) is the npm "latest". Its `package.json` `exports` map "." to `./lib/version.cjs` and also exposes `./unstable/sync`, so the classic `ts.transpileModule` call failed (local inspection of [npm typescript](https://www.npmjs.com/package/typescript)). The standalone `microsoft/typescript-go` repo is archived ([GitHub API](https://github.com/microsoft/typescript-go)).
- Direct TS acceptance: Deno (the deno.com site navigation describes it as a "Modern runtime for JavaScript and TypeScript") ([deno.com](https://deno.com/blog/cloudflare)); Andromeda ("Run TypeScript files directly with zero configuration") ([andromeda](https://github.com/tryandromeda/andromeda)); Hako ("built-in TypeScript type stripping") ([hako](https://github.com/andrewmd5/hako)); `@sebastianwessel/quickjs` ("execute JavaScript AND TypeScript code") ([repo](https://github.com/sebastianwessel/quickjs)); Porffor (zoo: "Optimizing AOT compiler for JavaScript/TypeScript") ([zoo](https://zoo.js.org/engines.json)); Hermes (TS syntax partly supported) ([hermes](https://github.com/facebook/hermes)); Supabase Edge Runtime ("JavaScript, TypeScript, and WASM services") ([edge-runtime](https://github.com/supabase/edge-runtime)). Requires pre-transpiling: LLRT ("must be bundled and transpiled to ES2023 ahead of time") ([LLRT](https://github.com/awslabs/llrt)), the raw Worker Loader (pre-bundled modules; `@cloudflare/worker-bundler` accepts TS) ([Dynamic Workers blog](https://blog.cloudflare.com/dynamic-workers/)), and Javy (the Shopify CLI compiles TS via esbuild) ([Shopify docs](https://shopify.dev/docs/apps/build/functions/programming-languages/javascript-for-functions)).
- Code Mode: "generates TypeScript type definitions from your tools for LLM context, and executes the generated JavaScript"; code is normalized via acorn ([codemode README](https://www.npmjs.com/package/@cloudflare/codemode)). The 2025 blog says "The LLM writes TypeScript" but does not say how types are handled ([Code Mode blog](https://blog.cloudflare.com/code-mode/)).

### Inferences
- Run the stripper in the **host** (Rust: `oxc_transformer` 0.158.0 or swc; Node: oxc-transform or amaro), not inside each sandbox. Loading a transformer per sandbox would add 50 to 600 ms and 20 to 70 MB, while a warm host stripper adds about 0.1 to 0.3 ms per script ([crates.io oxc_transformer](https://crates.io/crates/oxc_transformer)).
- Prompt the model for "erasable" TypeScript (no enums or namespaces), or ask for JS with JSDoc as Cloudflare does, so strip-only transforms never fail.

### Gaps
- No published oxc vs swc vs amaro comparison for small files was consulted (the search budget ran out); local numbers are from one script on a loaded host.
- Bun's native TypeScript execution was not re-verified from a primary source in this pass.
- The cost of type-checking (tsgo) per script was not measured.

## Embedded fetch/HTTP inside the sandbox vs host-provided fetch

### Takeaway
Engines (V8 via deno_core or isolated-vm, QuickJS, Boa, Goja, GraalJS) ship **no HTTP client**; the host injects `fetch` or tool functions. Runtimes that ship `fetch` gate it in very different ways. **workerd and Dynamic Workers** have the best model for agents: `globalOutbound: null` blocks all egress, or a gateway intercepts every request and injects credentials. **Deno** uses `--allow-net=host` (with 2026 bypass CVEs); **LLRT** uses `LLRT_NET_ALLOW`/`LLRT_NET_DENY`; **StarlingMonkey** depends on whether the Wasm host provides `wasi:http`. **Node** has only a "seat belt" `--allow-net`, and **Bun and txiki.js have no gating**.

### Cited Findings
| Runtime | HTTP client inside sandbox | Gating |
|---|---|---|
| Dynamic Workers / workerd | `fetch()`, `connect()` | `globalOutbound: null` throws; a `WorkerEntrypoint` gateway intercepts every `fetch`/`connect` and can inject secrets from `this.env`; Code Mode default `null` ([egress control](https://developers.cloudflare.com/dynamic-workers/usage/egress-control/), [codemode](https://www.npmjs.com/package/@cloudflare/codemode)) |
| Deno CLI | `fetch`, WebSocket, `Deno.connect` | `--allow-net[=host]`, `--deny-net` overrides; a bare `--allow-net` grants all ([Deno docs](https://docs.deno.com/runtime/fundamentals/security/)); 2026 bypasses CVE-2026-49859 / -49860 / -49411 ([advisories](https://github.com/denoland/deno/security/advisories)) |
| Deno Sandbox (microVM) | anything | `allowNet` enforced at the VM boundary by an outbound proxy; secrets are placeholders until sent to approved hosts ([Deno blog](https://deno.com/blog/introducing-deno-sandbox)) |
| Node | `fetch` (undici), `net` | `--permission` + `--allow-net`; "does not protect against malicious code" ([Node docs](https://nodejs.org/api/permissions.html)) |
| Bun | `fetch` | none ([PR 35779](https://github.com/oven-sh/bun/pull/35779)) |
| LLRT | `fetch` (partial), `net`, `dgram` | `LLRT_NET_ALLOW` deny-by-default allowlist; `LLRT_NET_DENY` precedence ([LLRT](https://github.com/awslabs/llrt)) |
| txiki.js | `fetch`, WebSocket, TCP/UDP | none described ([txiki.js](https://github.com/saghul/txiki.js)) |
| StarlingMonkey / ComponentizeJS | `fetch` over `wasi:http` | the host chooses whether to provide `wasi:http` (`wasmtime -S http`) ([StarlingMonkey](https://github.com/bytecodealliance/StarlingMonkey)) |
| Supabase Edge Functions | `fetch` (Deno) | ports 25 and 587 blocked ([limits](https://supabase.com/docs/guides/functions/limits)) |
| Boa (`boa_runtime` → `boa_wintertc`) | Request/Response API surface added in v0.22 | embedder-provided (inference) ([v0.22 release](https://github.com/boa-dev/boa/releases/tag/v0.22)) |
| @sebastianwessel/quickjs | host-injected `fetch` (`allowFetch: true`) | no allowlist described ([repo](https://github.com/sebastianwessel/quickjs)) |
| quickjs-emscripten, rquickjs, isolated-vm, deno_core, Javy, GraalJS, Goja | none | host-provided functions only ([quickjs-emscripten](https://github.com/justjake/quickjs-emscripten), [isolated-vm](https://github.com/laverdet/isolated-vm), [Shopify/Javy](https://shopify.dev/docs/apps/build/functions/programming-languages/javascript-for-functions)) |

### Inferences
- For benchmarking real HTTP, compare two shapes: (a) an in-engine `fetch` whose egress goes through a host gateway (workerd `globalOutbound`; Deno/LLRT allowlists), and (b) a host-provided `fetch` tool that the host implements with its own client (Rust `reqwest`/hyper or Node undici) and returns as a Promise. Shape (b) works with every B-group engine and keeps credentials and egress policy in one place. Its cost is one host-call round trip per request (1.4 µs in isolated-vm sync, 3.8 µs async; 8.6 µs in quickjs-emscripten), which is negligible next to network latency.
- Streaming response bodies through a host-provided `fetch` needs a chunked or async-iterator bridge; full buffering is simpler but caps memory per request. (inference)

### Gaps
- Whether Dynamic Workers default to open egress when `globalOutbound` is unset is ambiguous in the docs.
- Whether Boa 0.22 ships a working `fetch()` with a pluggable fetcher, or only the Request/Response types, was not verified.
- Convex `fetch` availability by function type was not verified.
