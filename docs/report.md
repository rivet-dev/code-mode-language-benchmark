# Waiting, not computing, separates agent scripting runtimes

Agent scripting runtimes differ most in **what a session costs while it waits on a tool**, so the benchmark should make held-open sessions, pending calls, and payload marshaling its headline measurements and treat interpreter speed as secondary. Real HTTP requests from this host took **27 to 574 ms** to first byte ([COVID CSV](https://raw.githubusercontent.com/datasets/covid-19/main/data/countries-aggregated.csv); [GitHub REST](https://api.github.com/repos/python/cpython/issues?per_page=100&state=all)), while measured runtime overhead per host call ran from **7.5 ns in Wasmtime to about 140 µs through Monty's Wasm worker**, and the fixed memory of one session spanned roughly 5,000-fold, from **about 16 KB for a Lua 5.5 state** and **94 KB for QuickJS in Wasm** to **1.15 MB for a V8 isolate** and **41 to 78 MB for Pyodide** ([wtbench][s-wt]; [monty_bench.mjs][s-monty]; [luamem.c][s-lua]; [qjs_measure.mjs][s-qjs]; [ivm_measure.js][s-ivm]; [pyodide_bench.mjs][s-pyodide]). The shortlist follows from that spread and from agentOS's two sandbox mechanisms: **Tier 1 is V8 isolates, QuickJS compiled to Wasm, Luau, a hardened Pyodide, CPython on WASI under Wasmtime, and Pydantic Monty**, with PUC Lua, native QuickJS, StarlingMonkey, simulated bash, SQL engines in Wasm, Rhai and Rune, hyperlight-js, and Group A process baselines as Tier 2 comparison points. Security findings prune harder than performance does: in-realm JavaScript sandboxes logged more than two dozen escape CVEs in 2026, and **Pyodide inside a Node realm reached the host shell through `ctypes` in a local test even with its `js` bridges blocked**, the flaw behind escapes in seven shipped products ([Cyera](https://www.cyera.com/research/sandcastles-not-sandboxes-how-one-architectural-flaw-exposed-seven-products); [pyodide_ctypes_check.mjs][s-ctypes]). Fluency evidence keeps the main benchmark on Python, JavaScript, Lua/Luau, bash, and SQL, and moves Rhai, Rune, Gleam, MoonBit, and array languages into an explicit documentation-plus-feedback experiment. The method is a slope, not a snapshot: cgroup `memory.current` with PSS and USS fitted against live session count at defined lifecycle states, cgroup CPU per completed script under an open-loop arrival schedule, and every scenario issuing real HTTPS to a pinned local fixture server through either the host HTTP engine or the runtime's own client. No public dataset reports memory per pending tool call or per idle session for any of these runtimes, so this benchmark would publish the first.

## Only Wasm, V8 isolates, and purpose-built VMs earn in-process trust

The classification asks one question: can the runtime itself stand between prompt-injected code and the host process? **Group B** runtimes pass on four counts at once: memory-safe containment (Wasm linear memory, a V8 isolate heap, or a memory-safe VM), no ambient authority because all I/O goes through host-provided functions, enforceable CPU and memory limits, and a design or production record aimed at hostile code. **B-conditional** runtimes are capability-limited by design but fail one count for a stated reason: a native C engine with a live CVE stream, a missing heap cap or interrupt, a default bridge into the host realm that must be removed, or code young enough that its own vendor recommends more isolation. **Group A** runtimes ship ambient file, network, or process access and need OS or VM isolation. The adversary is not hypothetical: Check Point chained a prompt injection into a Code Mode escape on a self-hosted build in 2026 and concluded that "prompt injection is a code-execution entry point" ([Check Point Research](https://research.checkpoint.com/2026/when-agentic-glue-melts/)).

Almost every language outside JavaScript reaches Group B only by running inside Wasm or a V8 isolate, because the maintainers of native interpreters disclaim in-runtime sandboxing themselves. Ruby made `$SAFE` "a normal global variable with no special behavior" ([Ruby 3.0 NEWS](https://docs.ruby-lang.org/en/3.0.0/NEWS_md.html)), PHP does not treat `open_basedir` bypasses as security issues ([PHP policies](https://github.com/php/policies/blob/main/security-classification.rst)), Perl says Safe compartments "are not supported as security mechanisms" ([perlsecpolicy](https://perldoc.perl.org/perlsecpolicy)), JEP 486 permanently disabled Java's Security Manager ([JEP 486](https://openjdk.org/jeps/486)), Microsoft says CAS "is no longer treated as a security boundary" ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/core/porting/net-framework-tech-unavailable)), DuckDB tells users to "treat SQL in DuckDB like code in Bash or Python" ([DuckDB](https://duckdb.org/docs/2.0/operations_manual/securing_duckdb/overview.html)), and Python's docs say not to use subinterpreters "in security-sensitive situations" ([Python docs](https://docs.python.org/3/library/concurrent.interpreters.html)). Full JavaScript runtimes are no different: Node's permission model "does not protect against malicious code" ([Node.js](https://nodejs.org/api/permissions.html)), Deno asks for a VM or microVM around untrusted code ([Deno](https://docs.deno.com/runtime/fundamentals/security/)), and Bun silently ignores Node's permission flags ([Bun PR 35779](https://github.com/oven-sh/bun/pull/35779)). The native exceptions were built for hostile input: Luau's sandbox targets code that may be "actively malicious" ([Luau](https://luau.org/sandbox)), Wikimedia runs untrusted Lua under memory and CPU limits ([LuaSandbox](https://www.mediawiki.org/wiki/LuaSandbox)), Rhai is "designed to not bring down the host system, regardless of what a script may do" ([Rhai](https://rhai.rs/book/safety/index.html)), and CEL is non-Turing-complete and evaluates in time linear in its input ([cel-go](https://github.com/cel-expr/cel-go)).

The security-focused designs are research or alpha. ### Group A pays for its boundary in milliseconds and megabytes

The OS boundary itself is cheap; the interpreter behind it is not. Launching through user, network, mount, and PID namespaces measured 2.8 to 6.4 ms in total against 0.98 ms for a bare exec, with no resident memory added ([results.json][s-results]), and both Anthropic's `srt` and OpenAI's Codex sandbox build on bubblewrap plus seccomp ([srt](https://github.com/anthropic-experimental/sandbox-runtime); [Codex](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)). For Python and JavaScript runtimes, the real Group A tax is 13 to 66 ms of interpreter startup and 2 to 14 MiB of private memory per process before the script allocates anything, which a pre-forked zygote removes and stronger boundaries add to.

## Escapes and fluency data prune the field before any benchmark runs

### Bridges and bindings, not engine cores, broke sandboxes in 2026

The most consequential finding concerns agentOS's current Python path. Under Node, Pyodide's Emscripten glue implements `system` as `child_process.spawnSync` with a shell and `emscripten_run_script_string` as `eval`, so `ctypes.CDLL(None)` hands guest Python the host's shell and JavaScript realm. A local test on Pyodide 314.0.7 and Node 26.13.1, with `js` and `pyodide_js` set to `None` in `sys.modules`, wrote a file through `system()` and read `process.version` through the script hook ([pyodide_ctypes_check.mjs][s-ctypes]). Cyera's DEF CON 34 research found the same flaw in seven products, including n8n (CVE-2025-68668, CVSS 9.9), Grist (CVE-2026-24002, 9.1), Cohere Terrarium (CVE-2026-61522, 9.3), and smolagents (CVE-2026-10613, 8.3), and concluded that "an FFI control is only effective if the dangerous symbol is unavailable" ([Cyera](https://www.cyera.com/research/sandcastles-not-sandboxes-how-one-architectural-flaw-exposed-seven-products)). Pydantic archived its Pyodide sandbox because "there's just no safe way to run Python within pyodide safely with reasonable latency" ([mcp-run-python](https://github.com/pydantic/mcp-run-python)), and smolagents removed its Pyodide executor as the CVE fix. An earlier internal note describes agentOS blocking `js` and `pyodide_js`, the exact pattern that failed elsewhere; the current agentOS driver was not inspected for this report, so **re-running the local test against agentOS is the cheapest high-value action in this plan**. Pyodide becomes Group B only in a realm with no Node APIs and with `ctypes`, `_ctypes`, and the Emscripten `system`, `popen`, `execve`, and `emscripten_run_script*` exports removed.

Every Emscripten language port in the catalog carries the same hazard in a different form. ruby.wasm passes `evalJs: (code) => Function(code)()` to the guest ([ruby.wasm](https://raw.githubusercontent.com/ruby/ruby.wasm/main/packages/npm-packages/ruby-wasm-wasi/src/vm.ts)), webR evaluates R-supplied strings with `(0, eval)(code)` and installs an XHR shim that can read `file:` URLs under Node ([webR](https://raw.githubusercontent.com/r-wasm/webr/main/src/webR/webr-worker.ts)), Trealla exposes `js_eval_json` ([trealla-js](https://github.com/guregu/trealla-js)), SWI-Prolog's `js_run_script` "uses eval" ([swipl-wasm](https://github.com/SWI-Prolog/npm-swipl-wasm)), and MicroPython's `js` module lets Python `await js.fetch(url)` ([MicroPython](https://github.com/micropython/micropython/blob/master/ports/webassembly/README.md)). The Wasm module is a sound boundary; its default bridge gives away the host realm. **Every Wasm port in the benchmark must run with its bridge replaced by tool shims**, and the reported numbers must be for that hardened configuration, not the default.

V8 holds up as an engine but not automatically as a product boundary. Check Point found memory-corruption bugs in workerd's C++ bindings in 2026 (a URLPattern out-of-bounds read and use-after-frees in zlib `deflateParams()` and HTMLRewriter) and chained a prompt injection into a Code Mode escape that ran shellcode, though only on a self-hosted build with the V8 sandbox disabled; its verdict was that "the engine is not the whole boundary" ([Check Point Research](https://research.checkpoint.com/2026/when-agentic-glue-melts/)). Cloudflare separately demonstrated a production Spectre leak of up to 12 bit/s and states that neither the V8 sandbox nor memory protection keys fully mitigates Spectre ([Cloudflare](https://blog.cloudflare.com/revisiting-spectre-attacks-on-workers/)). Self-hosted workerd says it "is not a hardened sandbox" ([workerd](https://github.com/cloudflare/workerd)), and isolated-vm, the main Node binding for isolates, is in maintenance mode, calls `memoryLimit` "more of a guideline" that attackers can exceed two to three times, and shipped a critical guest-reachable `ExternalCopy` type confusion in August 2026 ([isolated-vm advisory](https://github.com/laverdet/isolated-vm/security/advisories/GHSA-864f-rcv7-6rh4); [isolated-vm](https://github.com/laverdet/isolated-vm)). For agentOS this means every native binding exposed to guest JavaScript (compression, parsers, URL handling, storage) is part of the boundary and needs its own fuzzing.

Native C interpreters carry steady CVE streams that Wasm containment neutralizes. NVD lists seven QuickJS CVEs scored 6.5 to 8.8 published on a single day in October 2025 ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-62494)), and quickjs-ng published a critical RCE advisory for `js_array_toReversed()` in May 2026 ([quickjs-ng advisories](https://github.com/quickjs-ng/quickjs/security/advisories)); Figma moved plugins to QuickJS compiled to Wasm in 2019 because the Wasm VM's object representations are too different to confuse with host objects ([Figma](https://www.figma.com/blog/an-update-on-plugin-security/)). Redis's Lua had a CVSS 10.0 use-after-free reachable from crafted scripts ([Redis](https://redis.io/blog/security-advisory-cve-2025-49844/)), and native mruby has 43 tracked CVEs ([Debian](https://security-tracker.debian.org/tracker/source-package/mruby)). LuaJIT is worse for this use: its FFI "is not safe for use by untrusted Lua code" ([LuaJIT](https://luajit.org/ext_ffi_semantics.html)), and its instruction-count hook never fired inside a JIT-compiled infinite loop in a local test, while PUC Lua 5.5's hook stopped the same loop after 639 ms ([luamem.c][s-lua]). Luau publishes a threat model for hostile code with read-only globals, no bytecode loading, and a guaranteed-eventual interrupt, but imposes no memory limit by default, so the host must set one ([Luau](https://luau.org/sandbox)).

Wasm engines and their glue have records too. Wasmer published a Critical Singlepass miscompilation advisory leading to sandbox escape and a WASIX preopen-rights bypass in late 2026 ([Wasmer advisories](https://github.com/wasmerio/wasmer/security/advisories)), and eryx, the leading Rust wrapper for CPython on WASI, published two high-severity advisories, one letting guest-controlled file offsets make the host allocate gigabytes outside the configured memory cap ([eryx advisories](https://github.com/eryx-org/eryx/security/advisories)). In-realm restriction layers fail constantly: vm2 logged 13 escape CVEs from January to May 2026 and another critical wave in October ([Kodem](https://www.kodemsecurity.com/resources/vm2-sandbox-escape-vulnerabilities-the-2026-cve-wave-turning-ai-agents-into-host-rce-vectors)), SandboxJS nine critical escapes ([GitHub advisory](https://github.com/advisories/GHSA-g8f2-4f4f-5jqw)), RestrictedPython six advisories including two 2026 escapes ([RestrictedPython](https://github.com/zopefoundation/RestrictedPython/security/advisories)), and Node's docs say `node:vm` "is not a security mechanism" ([Node.js](https://nodejs.org/api/vm.html)). Deno's runtime-enforced permissions logged more than ten bypass advisories in 2025 and 2026, including a `fetch()` bypass through a missing DNS resolution check, which is precisely the egress control code mode would lean on ([Deno advisories](https://github.com/denoland/deno/security/advisories)).

These findings change what the benchmark reports. Netlify moved Edge Functions from V8 isolates to Firecracker microVMs in late 2026, arguing that "V8 isolates, no matter their name, do not provide this level of isolation" ([Netlify](https://www.netlify.com/blog/edge-functions-firecracker-microvms/)), while Cloudflare expanded isolate-based Code Mode the same year ([Cloudflare](https://blog.cloudflare.com/dynamic-workers)), so the trade between density and isolation strength is live and **every result row must carry its isolation level and enabled limits**. Pydantic's framing also applies to every runtime here: "code mode is not a sandbox," because tools still run with the agent's authority ([Pydantic](https://pydantic.dev/articles/code-mode-vs-sandboxes)), which makes capability checks at the tool boundary a requirement independent of the runtime choice.

### Frontier models write Python and JavaScript at ceiling and Lua close behind

Fluency limits the shortlist as much as security does. On EsoLang-Bench v2, GPT-5.4 at xhigh effort and Gemini 3.1 Pro solved 100% of 80 problems in both Python and JavaScript but only 0 to 11% of the same problems in esoteric languages, even with documentation in the prompt ([EsoLang-Bench](https://arxiv.org/html/2603.09678v2)). Every vendor shipping code mode at scale chose a T1 language: Cloudflare argued that LLMs "have seen a lot of code" but "have not seen a lot of 'tool calls'" and chose TypeScript ([Cloudflare](https://blog.cloudflare.com/code-mode/)), while Anthropic's Programmatic Tool Calling, OpenAI's Code Interpreter, Gemini, smolagents, and Monty use Python ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use); [Gemini](https://aistudio.google.com/docs/code-execution); [smolagents](https://huggingface.co/blog/smolagents)).

The levers that rescue a weaker language are execution feedback and worked examples, not documentation. jqBench and EsoLang-Bench found documentation in the prompt gave little or no gain, while interpreter feedback was the strongest strategy ([EsoLang-Bench](https://arxiv.org/html/2603.09678v2)); few-shot examples beat retrieved documentation in 7 of 12 Gleam and 8 of 12 MoonBit comparisons ([Giagnorio et al.](https://huggingface.co/papers/2606.16827)); and Anthropic's tool use examples raised complex parameter accuracy from 72% to 90% ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)). Feedback has a price paid in tokens: frontier agents solved 95 to 99% of the problems in OCaml but spent 1.28 to 1.69 times Python's tokens on error recovery, even though final solutions were similar in size ([Wu, Anderson, Guha](https://arxiv.org/html/2607.22807v2)). Static verbosity is a smaller effect: Clojure was the most token-efficient of 19 languages at 109 tokens per Rosetta task ([Alderson](https://martinalderson.com/posts/which-programming-languages-are-most-token-efficient/)), and writing TypeScript costs about 31% more tokens than JavaScript, almost all from annotations ([HackerNoon](https://hackernoon.com/we-measured-the-llm-token-cost-of-5-languages-typescript-costs-31percent-more-than-javascript)), which supports Cloudflare's pattern of typed declarations for the API and plain JavaScript for the script.

Code mode itself beats JSON tool calls for most current models, with a weak spot that the benchmark must probe. In a 14-model BFCL study with typed Python stubs, programmatic calling matched or exceeded JSON calling in 11 models, and in a fan-out probe at N = 100 on Claude Sonnet 5, JSON enumeration scored 0% against 100% for code; parallel categories still trailed JSON by 14.1 points, partly because some OpenAI models wrote literal `\n` sequences that broke the script, and GPT-4o fell 26.9 points ([Patel et al.](https://arxiv.org/html/2608.06370v1)). With code mode on, Pydantic measured long-horizon success between 58% and 100% across eight models, 92% or more for seven of them, at 58% lower cost, and warned that "a snippet that fails halfway and gets rerun can do its first half twice" ([Pydantic](https://pydantic.dev/articles/why-code-mode-is-the-future)). **The benchmark therefore needs a fluency arm**: first-attempt success, retries, and unsupported-feature hit rate per language against the same tool API, at least two model families, and tools that are idempotent or count duplicate side effects.

## Six Tier 1 runtimes map onto agentOS's V8 and Wasm paths

A runtime makes the shortlist when it is a credible boundary in its hardened configuration, its language is T1 or T2 (or it enters as an explicit fluency experiment), it embeds in a Rust or Node host, and its result changes a decision for agentOS. agentOS runs guest JavaScript in V8 isolates and compiled tools as Wasm in one process, so Tier 1 maps onto those two mechanisms: V8 isolates directly, four language runtimes delivered as Wasm (QuickJS, Luau, CPython on WASI, and Pyodide, which is itself Wasm inside V8), and Monty, which ships native and Wasm builds. **agentOS as shipped also belongs in the benchmark.** An internal August 2026 measurement on this host put its `javascript.execute` runtime at 90 ms to create, 330 ms for the first hello and 12 ms for the second, with the Node process at 88 MB RSS against about 40 MB for plain Node (internal notes, not published), against 3.1 ms and 1.15 MB for a bare isolated-vm isolate ([ivm_measure.js][s-ivm]). That gap suggests product overhead, not engine overhead, dominates per-session cost today, and the internal Secure Exec benchmarks show the same shape: mounting the Wasm command set took 173 ms and first guest execution 596 ms of a 773 ms cold start, and a shared sidecar degraded past 3 s under concurrent fan-out ([Secure Exec benchmarks][i-secureexec]).

The shortlist deliberately leaves out runtimes that fail the security test or cannot be compared fairly. ## Tool orchestration leads eighteen workload families and thirty-eight tasks

The workload evidence is lopsided in a useful way. Code mode exists to run host-tool orchestration, and the design documents agree on its shape: Cloudflare turns MCP schemas into a TypeScript API and runs each snippet in a fresh isolate ([Cloudflare](https://blog.cloudflare.com/code-mode/)), Anthropic's Programmatic Tool Calling saves 20 to 40% of tokens on production requests with 10 to 49 tool definitions ([PTC docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)), Manus averages about 50 tool calls per task ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)), and AppWorld solutions average 42.5 API calls ([AppWorld](https://arxiv.org/html/2407.18901)). Beyond tool calling, data processing, and artifact generation, the evidence supports separate axes for workloads that stress different costs. Large-result marshaling deserves its own row because converting a 0.5 to 50 MB tool result into guest objects, not the analysis, dominates it. Tool-catalog scaling matters because binding setup grows with catalog size, and real catalogs reach 1,280 operations for GitHub's REST API and 3,778 for Cloudflare's 28 MB spec ([GitHub spec](https://raw.githubusercontent.com/github/rest-api-description/main/descriptions/api.github.com/api.github.com.json); [Cloudflare spec](https://raw.githubusercontent.com/cloudflare/api-schemas/main/openapi.json); [specstats.py][s-spec]). Persistent sessions and idle waiting matter because platforms bill and expire by container time, so idle memory per session is likely the most important efficiency number for a host running many sessions. Utility compute (dates, HMAC, compression, regex redaction) appears in only a few percent of tasks but is where interpreters diverge most, since CPython, V8, and Rust ship native implementations that AST-walking sandboxes reimplement in the interpreter. Text search over files is the dominant bash-agent activity, and its cost is filesystem metadata rather than interpretation: `stat()` across 68,000 files made millisecond commands time out at 10 s until just-bash was optimized ([Vercel](https://vercel.com/blog/testing-if-bash-is-all-you-need)). Sub-LLM calls add multi-second waits inside a script, and cancellation and output caps exercise the kill path that every platform enforces.

The suite has three tiers so that every runtime gets a score. **Tier A** tasks need only host tools and a basic standard library; **Tier B** tasks need ecosystem libraries and each has a Tier A twin with the same expected output (T15 and T32, T30 and T33), because Monty has no third-party packages ([Monty limitations](https://pydantic.dev/docs/monty/limitations/)) and library-heavy work cannot run identically everywhere; **Tier C** replays the overlapping tasks as shell pipelines. Every task uses seed `20261113`, a fixed clock of `2026-10-31T00:00:00Z`, canonical JSON output (sorted keys, floats to 6 decimals) checked byte-for-byte against a reference implementation, and RE2-compatible regexes so that Python `re`, JavaScript `RegExp`, Rust `regex`, and Monty's `fancy-regex` agree. Each runs in two marshaling modes, a raw string the guest parses as PTC does and a host-parsed structured value as Cloudflare's `structuredContent` does ([PTC docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling); [Cloudflare docs](https://developers.cloudflare.com/agents/model-context-protocol/codemode/)), and records wall time, CPU-seconds, peak and steady memory, bytes crossing the boundary, bytes returned, and HTTP requests verified by the server's per-session counters.

All tasks run against a deterministic fixture server, "agent-fixture," over HTTPS with a benchmark CA installed in each sandbox, plus plain HTTP, keep-alive, optional gzip, and latency injected before headers through `?lat_ms=`. Its datasets are synthetic where determinism matters and pinned real resources where realism does: 500,000 seeded records of about 100 bytes each; GitHub-shaped issues in 1.3 KB and 4.3 KB profiles, matching a measured average of 4,342 bytes per GitHub issue ([GitHub API](https://api.github.com/repos/python/cpython/issues?per_page=100&state=all); [itemsizes.py][s-items]); 20 HTML pages sized to the Web Almanac's 35 KB median and 155 KB p90 plus two 1 MB pages ([Web Almanac](https://almanac.httparchive.org/en/2025/page-weight)); the 5.51 MB, 161,568-row COVID CSV ([datasets/covid-19](https://raw.githubusercontent.com/datasets/covid-19/main/data/countries-aggregated.csv)); Pride and Prejudice at 772 KB ([Gutenberg](https://www.gutenberg.org/cache/epub/1342/pg1342.txt)); a 4 MB PDF; the pinned GitHub and Cloudflare OpenAPI specs; CPython 3.14.0's `Lib/` with 2,388 files and 45.0 MB ([GitHub tree API](https://api.github.com/repos/python/cpython/git/trees/v3.14.0?recursive=1); [treestats.py][s-tree]); 68,000 synthetic issue files; 10,000 384-dimension vectors; and a dirty 100,000-row CSV. Redistribution licenses for the COVID CSV, the Cloudflare spec, and captured HTML still need checking, with synthetic look-alikes as the fallback.

### Three HTTP paths separate the host engine from embedded clients

Every scenario issues real HTTP over real TCP and TLS, but to the local fixture server rather than public endpoints, which add latency variance, rate limits, and CDN effects that would swamp the differences being measured. The fixture serves pinned copies of real resources, injects latency before headers, and counts requests per session so the harness can prove each scenario hit the network; an optional internet profile replays the same tasks against the pinned public endpoints as an unscored realism check. Requests travel one of three paths.

| Path | What happens | Where it applies | What to measure |
|---|---|---|---|
| H1, host tool on the host HTTP engine | The guest calls a tool such as `get_item()`; agentOS's engine (reqwest/hyper in Rust, undici in Node) handles TLS, pooling, and decompression, then returns a string or parsed value | Every runtime, and the only path for engines with no client: deno_core, QuickJS, Luau, Monty, isolated-vm ([isolated-vm](https://github.com/laverdet/isolated-vm); [Monty security](https://pydantic.dev/docs/monty/concepts/security/)) | Host CPU per request; bytes marshaled; reuse of one shared pool |
| H2, guest `fetch` routed through host egress | A guest-visible `fetch` or `curl` whose transport is a host binding that enforces allowlists and injects credentials | workerd `globalOutbound` ([Cloudflare](https://blog.cloudflare.com/dynamic-workers)); Pyodide `pyfetch` and urllib3 over JS fetch ([urllib3](https://urllib3.readthedocs.io/en/stable/reference/contrib/emscripten.html)); StarlingMonkey over `wasi:http`; eryx's allowlisted sockets ([eryx](https://github.com/eryx-org/eryx)); bashkit's injectable transport ([bashkit](https://docs.rs/bashkit/latest/bashkit/)) | Guest-side parsing and decompression cost; policy overhead |
| H3, runtime-embedded client | The guest owns HTTP parsing, TLS, and its connection pool inside its boundary | CPython requests or urllib3 with OpenSSL in a Group A process; Node, Deno, or Bun `fetch` in a subprocess; Pyodide's experimental raw sockets ([Pyodide 314](https://blog.pyodide.org/posts/314-release/)); WASIX sockets in Wasmer | Pools and TLS handshakes per session; `memory.stat sock`; memory per in-flight request |

H3 is unavailable for most Group B engines, so the matrix records it as unsupported rather than skipping it silently, and M13 compares paths only where at least two exist. Decompression is a real cost that moves between host and guest: measured wire-to-decoded ratios ran from 2.8 times for plain text to 6.3 to 6.9 times for GitHub JSON and Wikipedia HTML ([GitHub REST](https://api.github.com/repos/python/cpython/issues?per_page=100&state=all); [Wikipedia](https://en.wikipedia.org/wiki/Python_(programming_language))), so an embedded client pays gzip and TLS inside the sandbox while the host path marshals already-decoded bytes. Run keep-alive on and off, pool sizes of 1, 6, and unlimited, and TLS on and off; a rustls session peaked near 13 KiB against about 69 KiB for OpenSSL in a December 2023 benchmark ([ISRG](https://www.memorysafety.org/blog/rustls-performance/)), so per-session client pools multiply TLS state quickly.

### The async model decides what a pending call costs

How a runtime parks a guest on a pending tool call decides both the memory per pending call and whether parallel fan-out is possible at all. Language-level suspension over host promises is cheapest because a parked call is just heap objects: about 0.4 to 0.6 KB per awaiting V8 async function and about 0.8 KB through isolated-vm ([await_cost.js][s-await]; [ivm_measure.js][s-ivm]), about 0.6 KB in QuickJS ([qjs_measure.mjs][s-qjs]), and 1.1 KB per Lua 5.5 coroutine, which mlua bridges to Rust futures with `create_async_function` ([luamem.c][s-lua]; [mlua](https://docs.rs/mlua/latest/mlua/struct.Lua.html)). JSPI switches stacks natively at an estimated 1 µs per call ([V8](https://v8.dev/blog/jspi)) but is on by default only from Node 25; Pyodide's `run_sync` requires it, and `can_run_sync()` returned false on Node 22 without a flag and true on Node 26 ([pyodide_bench.mjs][s-pyodide]; [Pyodide](https://blog.pyodide.org/posts/jspi/)). Asyncify works everywhere but costs code size and speed, and quickjs-emscripten's asyncify build "can only suspend to wait for a single asynchronous call at a time," which rules out `Promise.all` fan-out on that path ([quickjs-emscripten](https://github.com/justjake/quickjs-emscripten)). Synchronous Wasm imports need Wasmtime fibers, measured at about 11 KiB resident per suspended guest and 0.55 µs per suspension, plus a 2 MiB stack reservation per guest under the on-demand allocator ([wtbench][s-wt]); WASI 0.3's component-model async, on by default since Wasmtime 46, is the route to many concurrent calls inside one instance ([Bytecode Alliance](https://bytecodealliance.org/articles/WASI-0.3)). The costliest model blocks a thread: webR's `eval_js(await=TRUE)` parks its whole worker on `Atomics.wait` ([webR](https://raw.githubusercontent.com/r-wasm/webr/main/src/webR/webr-worker.ts)), and Rhai has no async, so each waiting Rhai session needs a thread with Rust's 2 MiB default stack ([Rust std](https://doc.rust-lang.org/std/thread/index.html#stack-size)). Built-in caps shape fan-out too: Monty allows 1,000 suspensions per checkout by default and Pydantic AI 100 nested tool calls per `run_code` ([Monty limits](https://pydantic.dev/docs/monty/concepts/resource-limits/); [Pydantic](https://pydantic.dev/articles/code-mode-vs-sandboxes)). The matrix tests all of this directly: serial latency should approach k(D + o) and parallel latency D + k·o for k calls of delay D and overhead o, so any deviation exposes a runtime that serializes awaits at the boundary.

## Marginal cost is a slope across live sessions, never a single snapshot

Run every experiment on a dedicated Linux host rather than this shared machine, with the performance governor, turbo and SMT off, and cores partitioned among the system under test, the load generator, and the HTTP server; record CPU model, kernel, THP and KSM settings, swap, and every runtime version and build flag, including V8 pointer compression, jitless, and sandbox settings, the Wasmtime `Config`, and the allocator. Give each experiment its own transient cgroup (`systemd-run --user --scope -p MemoryAccounting=yes -p CPUAccounting=yes -p AllowedCPUs=... -p MemorySwapMax=0`), with the load generator and HTTP server in sibling cgroups, because cgroup v2 reports `memory.current`, `memory.peak`, `memory.stat`, and `cpu.stat` per group and charges page cache to whichever group touched it first ([cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)). Each runtime gets a session driver with one contract (`create()`, `run(script)` with host tools bound, awaits of host calls, `destroy()`), and the guest scripts are ported idiomatically with identical algorithms, following the Are We Fast Yet rule ([AWFY](https://github.com/smarr/are-we-fast-yet)).

**Delta RSS above baseline needs a precise definition to be comparable.** The baseline is the host harness, Rust or Node, with the engine loaded, zero sessions, and quiesced memory (state S0). Sessions are measured at defined lifecycle states: S1 created and idle; S2 after a reference script of ten tool calls returning 1 KB each plus aggregation; S3 suspended with 1, 10, or 100 pending host calls; S4 retained after the run and a GC; and the peak during S2. For 0, 1, 10, 100, 1,000, and 10,000 live sessions in a state, sample `memory.current` with its `memory.stat` breakdown (`anon`, `file`, `kernel`, `pagetables`, `kernel_stack`, `sock`, `shmem`), `smaps_rollup` (`Rss`, `Pss`, `Pss_Anon`, `Pss_File`, and USS as `Private_Clean` plus `Private_Dirty`), `VmSize`, and the runtime's own heap counter, once after forcing GC and purging the allocator (`malloc_trim(0)`, a jemalloc arena purge, `mi_collect(true)`, then a wait past the decay time) and once as-is, since production sees the natural value. Marginal cost is the slope b of metric(N) = a + b·N, fitted by OLS and Theil-Sen over at least five fresh-process repetitions with a bootstrap 95% interval and residuals that expose step functions such as arena growth and pool slabs; the gap between the OS slope and the runtime-heap slope is native, allocator, and binding overhead. PSS divides each shared page among its sharers while USS is what killing one session frees ([Linux proc](https://docs.kernel.org/filesystems/proc.html)), so report both for anything built on snapshots, copy-on-write images, or zygotes, and re-check after S2 because writes break sharing. Always publish the intercept beside the slope, because pools and zygotes move cost from b into a, and the honest comparison is total memory at the target concurrency.

| Quantity | Definition | Instrument |
|---|---|---|
| Baseline | Host harness with engine loaded, zero sessions, quiesced (S0) | cgroup `memory.current`; `smaps_rollup` |
| Marginal memory per session | Slope b over live sessions at S1 to S4, with bootstrap 95% interval | `memory.current` and `memory.stat`; ΣPSS; USS slope |
| Fixed cost | Intercept a: engine, pools, zygotes, snapshots | Same fit |
| Memory per pending call | Slope over 1 to 1,000 pending host calls in one session (S3) | Same, plus runtime heap counters |

| Virtual footprint | `VmSize`, mapping count, page-table slope | `/proc/PID/status`, `/proc/PID/maps`, `memory.stat` |
| CPU per script | Δ`usage_usec` divided by completed scripts at a fixed open-loop rate, user and system split | `cpu.stat`; per-thread `schedstat` |
| Per-call overhead | time(n, s) = c + n(t_call + s·t_byte) for n up to 10,000 and s of 0, 1 KB, 1 MB, per encoding | In-process timers; `perf stat` |
| Idle CPU | CPU-seconds per waiting session-hour, target near zero | `cpu.stat`, `schedstat`, `perf` over the idle window |
| Capacity | Scripts per second per core at the p99 target under a 2-CPU `cpu.max` | Open-loop generator with HdrHistogram |
| HTTP cost | CPU per request, memory per in-flight request, connections, TLS handshakes, socket memory, bytes across the boundary | Server counters, `ss`, `memory.stat sock` |

**CPU under load** is cgroup `cpu.stat usage_usec` per completed script at a fixed arrival rate below saturation, attributed per thread through `/proc/PID/task/*/schedstat` so that guest execution, the host event loop, and V8 GC or compiler threads separate; runtimes use helper threads, so CPU time can exceed wall time ([plb2](https://github.com/attractivechaos/plb2)). Host-call overhead comes from a no-op host function called n times at 0 B, 1 KB, and 1 MB, repeated for each encoding (JSON text, structured clone, CBOR or MessagePack, direct handles, ArrayBuffer transfer). Report cold (new process), warm-engine (new session in a warm process), and hot (reused session) separately, and make first-execution CPU the headline, because code-mode scripts run once and only 30 to 43.5% of VM and benchmark pairs consistently reached a steady state across 30 process executions in Barrett et al. ([arXiv](https://arxiv.org/abs/1602.00602v6)). Use at least 10, preferably 30, fresh process executions of at least 10 iterations each, medians with bootstrap intervals, and Mann-Whitney U for A/B comparisons as Sightglass does ([Sightglass](https://github.com/bytecodealliance/sightglass)), with absolute values always reported beside ratios.

**Load must be open-loop.** A closed loop sends only after a response arrives, so stalls go unmeasured; in wrk2's example a 1.4 s pause produced an uncorrected p99 of 6.04 ms against a corrected 1.27 s ([wrk2](https://github.com/giltene/wrk2)). Precompute a constant or Poisson arrival schedule, k6's `constant-arrival-rate` model ([k6](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)), measure latency from each intended start, record per-phase HdrHistograms (queue wait, session acquire, guest run, each host call, total), and merge histograms rather than averaging percentiles. Sweep from 10% to 120% of saturation under a two-CPU budget (`cpu.max` of `200000 100000` plus a cpuset), report scripts per second per core at a p99 target such as twice the unloaded p99, and derive memory at that operating point from Little's law: in-flight sessions equal arrival rate times mean latency, multiplied by the per-session slope. Idle behavior gets its own run, holding N sessions on host calls that resolve after 10 to 240 s and confirming that CPU stays near zero, with `schedstat` or `perf stat` across the window to catch hidden timers and polls.

Every run uses production limits, because metering costs CPU: locally, Wasmtime epoch interruption added 14% and fuel 84% to a tight loop ([wtbench][s-wt]). Use the budgets platforms already ship, 128 MB per Workers isolate ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)), 256 MB for Supabase Edge Functions ([Supabase](https://supabase.com/docs/guides/functions/limits)), and Pydantic AI's 30 s and 256 MiB per `run_code` ([Pydantic](https://pydantic.dev/articles/code-mode-vs-sandboxes)), and test enforcement itself with T28: a typed error within the limit plus 100 ms, memory back within 5% of baseline after the kill, and the p99 effect on 100 co-located sessions. Measure memory growth over 10,000 unique scripts as well as 10,000 sessions, because every LLM-written script is new and Redis warns that generating scripts at runtime "may, and probably will, exhaust the host's memory" through its script cache ([Redis](https://redis.io/docs/latest/develop/programmability/eval-intro/)). For HTTP, run a small hyper or axum server (or [go-httpbin](https://github.com/mccutchen/go-httpbin)) on its own cores and cgroup with HTTP/1.1 and h2, TLS from a local CA so verification stays on, and per-request delay, size, chunking, status, and close controls, and inject RTTs of 0.1, 1, 20, and 80 ms with `tc netem` on a veth pair between network namespaces or with Toxiproxy ([tc-netem](https://man7.org/linux/man-pages/man8/tc-netem.8.html); [Toxiproxy](https://github.com/Shopify/toxiproxy)). Each result row carries runtime, state, workload, fixed cost a, marginal b with its interval, peak, CPU per script, p50 and p99, maximum rate under the budget, isolation level, and enabled limits, with raw JSON and configuration published.

Four observations stand out. **First, isolation style rather than language sets the per-session floor**: a Lua state (16 KB) sits more than an order of magnitude below QuickJS with its own Wasm module (259 KB) and a V8 isolate (1.15 MB), and two to nearly four below every real CPython (3.5 to 9.5 MB) and Pyodide (41 to 78 MB). Contexts sharing an isolate (160 KB) and runtimes sharing one Wasm module (94 KB) are cheaper only because they are not boundaries between scripts. **Second, pending calls are cheap wherever suspension is a heap object**: at 0.4 to 1.1 KB per pending call in V8, QuickJS, and Lua, a 1,000-way fan-out costs about a megabyte, a design that parks a whole Wasmtime fiber per pending call pays about 11 KiB each (about 11 MB per 1,000), and Pyodide's `asyncio.gather` over 1,000 host promises added at most 0.4 MB. **Third, host-call overhead is irrelevant to wall time at real latency** (even Monty's 140 µs is under 0.05% of a 300 ms call) but matters for CPU in long serial chains, where 1,000 calls through Monty's worker spend about 63 ms on IPC alone. **Fourth, address space is a ceiling before RAM** for designs that give each session its own Wasm memory: V8 reserves 8 to 10 GiB per memory and refused new instances at 13,060 and 16,320 live memories ([node-wasm-and-pyodide-output.txt][s-nodewasm]), and Pyodide reserved 16 GiB per instance ([pyo-measure.mjs][s-pyo]). QuickJS's 94 KB figure comes from many runtimes created inside one shared Wasm module and linear memory ([qjs_measure.mjs][s-qjs]), so, by inference from that layout, a QuickJS memory-corruption bug in one session could reach its neighbors in that memory though not the host; the benchmark prices only the instance-per-session layout.

Compute tiers matter only for the analysis and utility tasks, and the probes rank them roughly. On recursive `fib(25)`, CPython 3.14 took 6.7 ms against 20.7 ms for CPython on WASI, 21 ms for Pyodide, 41.8 ms for Monty's native worker, and 168 ms for MicroPython, while Monty beat CPython on a simple loop at 49.2 against 74.5 ms ([native_bench.py][s-native]; [wasi_bench.py][s-wasi]; [pyodide_bench.mjs][s-pyodide]; [monty_bench.mjs][s-monty]; [micropython_bench.mjs][s-mpy]). Wasmtime's Pulley interpreter ran a compute loop 31.7 times slower than Cranelift ([wtbench][s-wt]), and published data puts V8 with JIT about 18 times faster than V8 jitless, which is about 2.5 times QuickJS ([javascript-zoo](https://zoo.js.org/engines.json)). Pyodide's library lane is expensive: on Node 26, importing pandas took about 2.5 s and added 178 MB, against 242 ms and 61 MB on native CPython 3.14 ([pyodide_bench.mjs][s-pyodide]; [native_bench.py][s-native]). TypeScript stripping belongs in the host: oxc-transform stripped a 42-line agent script in 101 µs warm after a 52 ms cold load, Node's built-in stripper took 259 µs, and `node --jitless` cannot strip TypeScript at all because its stripper needs Wasm ([ts_bench.js][s-ts]; [agent_script.ts][s-agentts]; [Node.js](https://nodejs.org/api/typescript.html)).

## The missing numbers are exactly the ones code mode depends on

The core metrics of this benchmark do not exist publicly for any candidate: memory per pending tool call, memory per idle session, and marshaling cost per megabyte. Vendor density figures are hypotheses to reproduce with the slope method, among them Cloudflare's "a few megabytes" per isolate ([Cloudflare](https://blog.cloudflare.com/dynamic-workers)), Monty's "about 2 MB baseline per worker" against the 9.5 MB RSS measured here ([Monty alternatives](https://pydantic.dev/docs/monty/reference/alternatives/)), and celld's 0.35 to 0.47 MB per shared-isolate tenant ([celld](https://celld.dev)). Unmeasured runtimes include Luau's per-state memory, coroutine size, and host-call cost; Monty in process through its Rust crate; native quickjs-ng; deno_core with a custom snapshot, pointer compression, and the V8 sandbox; StarlingMonkey, hyperlight-js, eryx, kobako, ruby.wasm, webR, DuckDB-Wasm, and PGlite per-instance memory; and embedding costs for Wasmer, WasmEdge, WAMR, and wasmi. The tiny-module Wasmtime figures are a floor, not the cost of a realistic guest such as QuickJS or CPython compiled to Wasm.

The Python path has its own open questions. No data exists for 1,000 slow host calls on CPython on WASI or in-process Monty, Pyodide documents no per-instance memory cap, its memory-snapshot API is private, and the memory held by a suspended JSPI stack is unpublished. A snapshot shortened Pyodide's start roughly tenfold but raised resident memory, because V8 copies the snapshot into each instance's Wasm memory instead of mapping it copy-on-write, so snapshots likely fix Pyodide's latency but not its density; that is an inference the benchmark should confirm, including with numpy loaded before the snapshot.

The workload and model evidence is thin where code mode is concerned. No vendor publishes the distribution of tool calls per script, script length, run time, payload size, or serial-versus-parallel share for Code Mode, PTC, or Monty, no replayable corpus of code-mode scripts exists, and the fixture's latencies are single values rather than measured tool latency distributions. On the model side, nobody has measured how often LLM-written code hits unsupported features in Monty, Starlark, or a stripped Luau, compared typed against untyped tool stubs, or run the same code-mode harness in Python against TypeScript; published token comparisons use only OpenAI tokenizers, and Rhai, Rune, Wren, and Roc have no fluency evidence at all.

A few methodology and verification items remain open as well. A 2026 kernel patch reports that resetting `memory.peak` on one file descriptor clobbers other readers, and whether it merged is unconfirmed ([LKML](https://lkml.iu.edu/2607.3/13090.html)), so use one descriptor or one cgroup per reading. Hardware counters may be unavailable on cloud VMs, which argues for bare metal. No public data compares memory per in-flight request for undici, reqwest/hyper, urllib3, and Pyodide's fetch bridge, and the rustls and OpenSSL per-connection numbers date from December 2023. Most urgently, the hardening state of agentOS's own Pyodide driver is unverified.

## Conclusion

The evidence reframes the original question. "Most efficient scripting language" for agents turns out to mean **the cheapest thing to hold open while a tool call is in flight**, and that is decided by isolation style and async model far more than by language: a V8 promise or a Lua coroutine parks a pending call in about a kilobyte, a Wasmtime fiber in about eleven, and a Pyodide session costs forty megabytes before it awaits anything. The headline metric should therefore be concurrent waiting sessions per GiB at a p99 target with production limits on and isolation level stated, with compute throughput as a secondary column that matters only for analysis and utility tasks. The snapshot data adds a structural point that is easy to miss: Wasmtime maps copy-on-write memory images, while V8, as far as the sources show, offers no file-backed mapping into Wasm memory and so copies a restored snapshot into every instance, which means **the Wasm engine that hosts a guest, not the guest's language, decides whether snapshots can ever make Python sessions cheap**.

For agentOS, the likely outcome is a portfolio rather than a single winner. V8 isolates stay the JavaScript path, with context-per-session density weighed against isolate-per-session safety and every native binding audited; Python splits into a code-mode lane (Monty or CPython on WASI) and a library lane (hardened Pyodide, or a forked CPython zygote under OS isolation) whose 40 to 80 MB per session only pandas-class work justifies; and Luau is the density option that must first pass a fluency check against the real tool API, since the main Luau-specific evidence is a community benchmark where frontier models score 74 to 80%. Two actions should precede the first benchmark run: confirm that agentOS's Pyodide guests cannot reach `ctypes` or the Emscripten exports, and instrument agentOS as shipped, because its measured 90 ms create time and roughly 48 MB above plain Node per runtime dwarf the engine floors this report compares.
